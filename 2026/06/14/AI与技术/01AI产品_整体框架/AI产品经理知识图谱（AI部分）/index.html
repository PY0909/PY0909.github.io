一、大模型知识基础

1.1 大模型分类全图谱

大模型基本原理

大语言模型（LLM）的核心操作就一件：预测下一个词。给它”今天天气真”，它算”好”的概率比”坏”高，就输出”好”。重复几千亿次训练后，模型学会了语法、逻辑、常识。

不需要数学，只需理解三个概念：

  • 训练数据 = 模型读过的所有书和网页，决定它的知识边界
  • 参数 = 模型的”脑容量”，参数越大越聪明，但也越贵越慢
  • 推理 = 你输入文字，模型逐字生成回复

1.2 大模型的核心概念

Token 与上下文窗口

Token 是计价和阅读单位，中文约 0.5 字/Token；上下文窗口是模型一次能看到的 Token 上限。窗口大 ≠ 要用满，历史会被重复计费

流式输出（Streaming）

AI 逐字输出的底层机制：服务器通过 SSE 一个字一个字推送，不等全生成完。非流式 = 等几秒一次性出全文

Temperature

控制输出的随机性。温度越低越稳定（写代码用 0），温度越高越发散（写诗用 1.2），日常聊天用 0.7

Top-P

核采样，限制候选词的概率范围。和 Temperature 类似，通常二选一调即可

System Prompt

设定 AI 的人设和行为边界，对话开始时发送。与 User Prompt 分工：System Prompt 定规则，User Prompt 提问题

结构化输出

强制 AI 以 JSON 等固定格式返回，对接程序或批量数据处理时必备

模型局限：三个天花板

幻觉：自信编造不存在的事实；知识截止：训练数据有日期限制；偏见与越狱：安全策略可能被绕过

选型与成本

简单任务用便宜的，写代码用 Claude，中文优先国内模型。Benchmarks（MMLU/HumanEval/Arena）衡量模型能力

1.3 Prompt 工程

ROLE 框架

R=角色，O=输出格式，L=限制，E=示例。角色越具体输出越精准，好 Prompt 是改出来的：写→看输出→改→再试

Few-shot

给 2-3 个范例再提问，模型会模仿格式和语气，输出质量大幅提升

Zero-shot

不给范例直接问，省事但效果弱于 Few-shot。简单任务可用，复杂任务优先 Few-shot

思维链（CoT）

加一句”请一步步分析再给结论”，强制模型展示推理过程，避免跳逻辑直接猜答案

结构化模板

用 Markdown 分块写清角色、任务、输出格式、约束条件，复杂任务不结构化易遗漏要求

工具描述工程

Agent 配置中，工具的描述用词直接影响调用准确率，描述越精确效果越好

常用模式

说要什么比说不要什么好，给范例比解释规则好，复杂任务拆多轮比塞一条长 Prompt 好

常见反模式

一次塞太多要求导致质量下降，Prompt 过于模糊输出不可预测，用否定句反而强化负面

2.2 API Key 与 Token

API Key 是什么

身份令牌。每次调用 AI 厂商的服务，请求里带上 Key，厂商靠它识别”是你，从你账户扣钱”
流程：你的终端发请求 → 服务器读 Key → 查账户余额 → 余额够就跑模型 → 按 Token 扣费

怎么拿到 Key

DeepSeek：platform.deepseek.com
流程：注册 → API Keys → 创建 Key → 复制保存 → 充值最低 10 元即可调用。其他平台流程类似
阿里通义：dashscope.aliyun.com
字节豆包：console.volcengine.com
Google Gemini：aistudio.google.com

怎么用

写到终端配置文件 ~/.zshrc：export DEEPSEEK_API_KEY=”sk-xxx”，保存后 source ~/.zshrc 生效。Claude Code 等工具自动读取

绝对不能做的事

Key 硬编码在代码文件里：git push 到 GitHub 后几秒内就会被自动化脚本扫走盗刷
截图发朋友圈：Key 暴露，任何人看到都能用你的额度
前端代码里放 Key：浏览器 F12 就能看到，完全裸奔
同一 Key 多人共享：出问题分不清是谁，额度被谁用完也不知道
铁律：API Key 只存在于环境变量中，永远不进入代码仓库

Token 计费

Token 是计价单位，不是字数。中文约 0.5 字/Token，英文约 0.75 词/Token。输入（你发的）便宜，输出（模型回的）贵 2-5 倍
产品视角：怎么估算 Token 成本
单次成本 =（输入 Token × 单价）+（输出 Token × 单价）。月成本 = 30 × 日调用量 × 单次成本。用 P95 不用平均值——100 次排序取第 95 名的值，覆盖 95% 场景。关键变量：日活 × 人均调用 × 每次 Token 消耗。上线前先打点跑一周拉基线
来源：Google SRE 手册《Monitoring Distributed Systems》明确指出监控系统延迟和资源消耗应使用百分位而非平均值。sre.google/sre-book/monitoring-distributed-systems/
模型选型：花多少钱取决于任务难度

简单任务（分类、摘要、提取）用小模型，百万 Token 几分钱。复杂推理（写代码、长文档分析）才上大模型，百万 Token 几块钱。选错了就是十倍百倍的价格差。

三、RAG 与知识增强方案

3.1 为什么需要 RAG：模型知道什么、能读什么

直接把文档丢给模型让它回答，为什么行不通？两个原因：知识它不知道，格式它读不了。

知识的局限

知识截止：训练数据有截止日期，模型不知道训练之后发生的事
幻觉：模型会自信地编造不存在的事实，因为它是预测下一个词，不是查数据库
私有知识盲区：模型不知道你的公司文档、个人笔记、项目资料
专业深度不足：通用模型在垂直领域深度不够，需要专业文献增强

格式的局限

纯文本模型能读：Markdown、JSON、HTML、纯文本 txt、代码文件、CSV
纯文本模型读不了：PDF、Word docx、Excel xlsx、图片、音频、扫描件。这些格式需要先提取文字
视觉模型能读图片，但原理是把像素编码成 Token 和文字混在一起理解，不是打开文件。给 100 页扫描件 PDF，Token 直接炸掉
所以 RAG 做的不只是知识注入，还有格式转换——文档预处理成 Markdown → 切块 → 向量化 → 存入知识库

3.2 知识预处理：让文档变成模型能读的格式

RAG 的第一个瓶颈不是检索算法，是文档格式不对。3.1 讲了纯文本模型只认 Markdown / JSON / HTML——但你的资料是 PDF、Word、PPT、Excel。预处理就是把这些格式统一转成 Markdown。

PDF

PDF 路径一：纯文字型
论文、合同、报告这类以文字为主的 PDF
处理方式：直接提取文字，工具 PyMuPDF4LLM 或 Docling，输出一个纯 Markdown 文件
PDF 路径二：复杂工程型
技术说明书、产品手册——里面有大量图纸、logo、表格、数据图表
处理方式：调用 OCR 视觉模型，提取文字 + 抽取所有图片。工具 Docling 或 MinerU
输出结构：文件夹含 imgs/ 图片子目录 + doc.md（内嵌图片路径），打开 doc.md 即可看到完整图文

Word docx

相对简单。Python-docx 或 Docling 直接提取文字 + 表格 + 标题层级，输出 Markdown。格式导出通常不会丢信息

PPT

每页幻灯片是一块，按页码 + 标题提取。难点是图片里的文字需要 OCR。Docling 支持 PPTX → Markdown

Excel xlsx / CSV

表格型数据。CSV 最简单直接可用，xlsx 需要工具提取每个 Sheet。转成 Markdown 表格格式，保留表头和数据行

HTML 网页

Jina Reader：网址前加 r.jina.ai/，自动扒掉广告和导航栏，返回干净 Markdown。专为 LLM/RAG 设计，免费额度够用
传统方案：html2text 或 pandoc 命令行转换，但需要自己写规则过滤导航栏和广告

核心原则：Garbage In, Garbage Out

预处理做不好，后续的切块、向量化、检索再精细也没用。文档转 Markdown → 统一格式 → 这才进入标准 RAG 流程

3.3 标准 RAG：索引 + 检索 + 生成

RAG 分两个阶段：索引（离线预备）和检索+生成（在线响应）。

阶段一：索引（离线，提前做好）
① 文档预处理：把 PDF/Word/网页等转成 Markdown 纯文本
② Chunking 切块：把长文档切成小段。固定大小最简单，语义切割最完整，滑动窗口避免边界丢失
③ Embedding 向量化：每段文字转成一个数学坐标，语义相近的文字坐标也近。模型：BGE（中文好）、text-embedding-3（多语言）、Jina（开源）
④ 存入向量数据库：Milvus 生产级，Qdrant 性能好，Pinecone 零运维，FAISS 轻量本地，Chroma 适合 demo
阶段二：检索+生成（在线，用户提问时触发）
⑤ 用户提问转向量 → 在向量库里找最相似的 N 段。检索策略：稠密检索语义好，稀疏 BM25 关键词准，混合检索生产标配
⑥ 检索结果 + 用户提问拼入 Prompt → 模型生成答案。关键规则：基于材料回答，材料里没有就说不知道，注明来源

3.4 七种高级 RAG

标准 RAG 好用但不够，复杂场景下这七种方案解决不同问题。

HyDE

提问太短信息不足 → 先用模型把提问扩展成假设答案，再用假设答案去检索，召回率更高

Multi-Hop RAG

答案散在多个文档 → 多次检索串联：找到线索 → 再搜 → 再串联，像查案一样层层递进

Self-RAG

检索到的材料不一定可靠 → 模型自己判断这段可信吗、有用吗，随时决定要不要再搜

Corrective RAG

检索质量不行时自动补救 → 先评估结果好不好，不够好就换策略重搜

Agentic RAG

流程需要灵活决策 → 模型自主决定什么时候搜、搜什么、搜几次、用不用工具

GraphRAG

跨文档全局关系 → 先把文档建成知识图谱，检索时沿图的关系找关联信息

HydraRAG

结构化 + 非结构化混合数据 → 文档 + 表格 + API 多源同时检索

文科生怎么用

不用写代码：Dify 拖拽式搭建，RAGFlow 深度文档解析，Cherry Studio 配好 Key 就用

四、智能体（Agent）

4.1 智能体是什么：从 LLM 到 Agent 的跨越

LLM 只能”回话”——你问，它答，一轮结束。Agent 能”做事”——你给目标，它自己规划步骤、调用工具、检查结果、修正错误。

核心公式：

LLM 和 Agent 的根本区别：

LLM Agent
能力边界 训练数据里的知识 训练数据 + 外部工具 + 实时信息
行为模式 一轮对话 多步自主执行
能用工具吗 ❌ ✅ 搜索、读写文件、调 API、跑代码
能自我纠错吗 ❌ ✅ 执行→检查→修正→再执行
典型场景 聊天、写作、翻译 写项目、做研究、自动化流程

这就是 Agent Loop（运行循环）——观察 → 思考 → 行动 → 观察新结果 → 再思考 → 再行动，直到任务完成。LLM 跑一圈就停了，Agent 跑完一圈自己决定要不要再跑一圈。

Agent Loop 与 ReAct 的关系

Agent Loop 是骨架——所有 Agent 的共性模式。ReAct（Reasoning + Acting）是填在骨架里的一套具体方法论——它在”思考”这一步强制 Agent 显式写出推理过程（”因为 X，所以应该做 Y”），然后再行动、再观察。

关系一句话：Agent Loop 定义了”会循环”，ReAct 定义了”怎么循环”。 后面 4.2 把 Loop 拆成五个组件，4.3 展开 ReAct 和其他范式的细节。

核心洞察：Agent 的有效能力

三个因子是乘法关系。任何一个接近零，整体崩塌：

  • 模型再强（换旗舰），接口薄弱（搜不到好数据、调不到工具），能力大打折扣
  • 模型强、接口广，但没有驾驭工程（没有验证、没有回滚、上下文管理混乱），长任务仍然崩塌
  • 所以 Claude Code 比裸调 API 强一个数量级——不是某一个因子赢了，是三个因子同时到位了

这个公式贯穿本章剩余所有内容：4.4 讲驾驭工程如何把第三个因子拉满，4.5 讲外部接口如何把第二个因子拉满。

4.2 五个核心组件：拆解 Agent Loop

Agent Loop 的每一段，由不同的组件负责。五个组件合在一起，Agent 才能跑起来。

① 大脑（LLM）

大脑负责 Agent Loop 里的**”思考”环节**。

每次循环，Agent 把观察到的东西（工具返回的结果、文件内容、对话历史）喂给大脑，大脑判断：现在处于什么状态？下一步该做什么？这个判断的质量，直接决定了 Agent 的表现。

4.1 已经讲过：Agent 的有效能力 = 模型 × 接口 × Harness。大脑是三个因子中的第一个。模型再聪明，接不到外部数据和工具，上限就被锁死。

② 记忆（Memory）

记忆负责 Agent Loop 里的**”我之前做了什么、我知道什么”**。

没有记忆，Agent 跑完一圈就忘了上一圈发生了什么。记忆分两种：

  • 短期记忆：当前会话的对话历史。代价是每次请求都要重新发送——Token 滚雪球的根源。
  • 长期记忆：跨会话持久化的知识。最简单的方案是一个 memory.md 文件，Agent 自己读写。进阶方案用向量数据库存储，按需检索。

每次 Agent Loop 转到”观察”这一步，记忆系统决定哪些历史信息应该被注入到上下文中——喂太多浪费 Token，喂太少 Agent 失忆。

③ 规划（Planning）

规划负责 Agent Loop 里的**”不只想到下一步，而是想清楚全局”**。

没有规划，Agent 就是想到哪做到哪——见一个坑填一个坑，填到第 20 个坑发现路线完全错了。规划让 Agent 在动手之前先问：

  • 总共要做多少件事？
  • 哪些先做、哪些后做？
  • 做完这一步，会观察到什么结果？下一步基于那个结果该怎么做？
  • 做到什么程度算”做完”？

回到 Agent Loop 的视角：规划不改变”观察→思考→行动”的结构，但它让”思考”不再是短视的、只盯着眼前一步的——而是有了全局地图。Plan-and-Solve 就是规划的最典型实现（4.3 展开）。

④ 工具（Tool Use）

工具负责 Agent Loop 里的**”行动”环节**。

大脑想好了”该做什么”，工具去执行。不调用工具的 Agent，就是另一个聊天框——只能想，不能做。常见工具类型：

  • 文件系统：读写 Markdown、CSV、JSON、日志
  • 终端：执行命令、运行脚本、Git 操作
  • 网络：调 API、搜索、爬页面
  • 数据库：查询、写入
  • 浏览器：打开网页、填表、截图、提取数据

工具设计的核心原则：少即是多。Claude Code 只暴露约 15 个核心工具——工具太多，Agent 选择困难；工具太少，Agent 没手没脚。

⑤ Skills（技能封装）

Skills 不是大脑（不负责思考），不是记忆（不负责记住），不是工具（不负责执行），不是规划（不负责排顺序）。Skills 是**”我知道怎么干这件事”**——把 System Prompt + 工具配置 + 领域知识打包成可复用的能力单元。

维度 大脑 记忆 规划 工具 Skills
管什么 思考判断 记住什么 先做什么 能调什么 知道怎么干
在 Loop 中的位置 Think 跨循环持久化 Think（全局视角） Act 跨组件打包

Claude Code 的 .claude/skills/ 目录、Hermes Agent 的自进化 Skill 生成——产业已经在用 Skills 来组织 Agent 的能力边界。Skills 回答的核心问题是：“这个 Agent 擅长什么场景？遇到什么情况该怎么处理？”

4.3 经典范式：Agent 怎么”想”和”做”

4.1 讲了 Agent Loop 是骨架，下面展开三种填在骨架里的具体方法论。看同一个任务——“帮我写一篇关于 AI 的行业简报”——每种范式各怎么跑。

ReAct（边想边做）

ReAct 让 Agent 在 Loop 的每一次”思考”环节显式写出推理过程，再行动，再观察。

ReAct 的核心：每一步都让你看到 Agent 在想什么。 不是黑箱决策，是可追踪的推理链。

Plan-and-Solve（先画地图，再走路）

ReAct 是边走边想，Plan-and-Solve 是先停下来画完整地图，再一口气走完。

Plan-and-Solve 的优势：不迷路，不跳步。代价：规划阶段多烧 Token，且如果计划本身有误，执行到一半才发现，浪费更大。

Reflection（做完回头看，自我纠错）

ReAct 和 Plan-and-Solve 都是”往前看”，Reflection 是”做完回头看”——把自我批评作为下一轮 Loop 的输入。

Reflection 的核心价值：自己查自己的错。 代价：多轮反省多烧 Token，但产出质量显著更高。

三种范式怎么选

场景 推荐范式 原因
任务路径清晰、步骤已知 Plan-and-Solve 规划一次，高效执行
任务路径不确定、需边做边看 ReAct 灵活调整，每步可见
对质量要求极高、可接受多轮迭代 Reflection 自我纠错，质量层层加码
复杂长任务 Plan+ReAct 混用 先规划框架，每步执行再用 ReAct

4.4 外部接口：Agent 的能力边界

回到 4.2 的核心公式：Agent 的能力上限 = 模型自身能力 × 外部接口的广度。模型再强，接不出去、拿不到数据、调不动工具，上限就被锁死。

① 文件系统

最朴素、最基础的外部接口——Agent 读写本地文件。没有它，Agent 连”把结果保存下来”都做不到。读写 Markdown、CSV、JSON、日志——一切本地持久化的根基。

② HTTP REST API

最通用的对外接口。万物皆可 HTTP：调天气 API、查数据库、发邮件、触发 CI/CD——只要对方提供一个 URL，Agent 就能接上。这是 Agent 集成外部服务的”普通话”。

③ WebSocket

HTTP 是”问一句回一句，结束”。WebSocket 是”一条通道建立后，双方随时发消息”。Agent 监控实时数据流（股价、日志、IoT 传感器）、多 Agent 之间持续通信，靠的就是它。

④ SSE（Server-Sent Events）

服务器主动向 Agent 推送事件流。所有 AI 模型的流式输出（你看到的逐字回复）底层就是 SSE。Agent 也可以用它接收外部系统的实时事件推送。

⑤ Function Calling / Tool Use

模型原生的工具调用能力。用 JSON Schema 定义”这个函数是干什么的、参数是什么”，模型自己决定什么时候调用、传什么参数。OpenAI 叫 Function Calling，Anthropic 叫 Tool Use——本质上是一回事：让模型长出”手”。

⑥ MCP（Model Context Protocol）

Anthropic 推出的标准化协议。在 Function Calling 之上加了一层协议抽象：一次编写 MCP Server，所有兼容模型都能调用。采用 Client-Server 架构，工具通过 JSON-RPC 2.0 注册和调用。定位：AI 界的”USB-C 接口”。

⑦ Computer Use

Anthropic 的”截图+鼠标键盘”方案。模型接收屏幕截图 → 理解像素内容 → 输出鼠标点击坐标和键盘输入。这让 Agent 能操控任何有 GUI 的应用，不局限于有 API 的服务。

⑧ 浏览器操控（CDP / Playwright）

DOM 级别的浏览器控制。和 Computer Use 的”看截图猜坐标”不同，这条路直接操纵浏览器的文档对象模型——精确点击元素、填写表单、提取数据。Browser Use、Playwright MCP 都走这条路。

对比 Computer Use 浏览器操控（CDP）
原理 截图→视觉理解→坐标操作 DOM→元素定位→精确操控
精度 依赖视觉识别 元素级别精确
适用范围 任何 GUI 应用 仅浏览器
代表 Anthropic Computer Use Browser Use, Playwright

⑨ A2A（Agent-to-Agent Protocol）

Google 推出的 Agent 间协作协议。不同厂商、不同框架的 Agent 通过 Agent Card（.well-known/agent.json）相互发现、委托任务、追踪结果。如果说 MCP 是 Agent 的”手”，A2A 就是 Agent 之间的”协作语言”。

4.6 Vibe Coding：AI 时代的核心能力

一个朴素的认知

大多数人还没有真正用好 AI。不是因为学不会 Prompt、不是买不起工具——是缺少一个”用 AI 解决问题”的环境。

没有环境，再好的工具也只是聊天框。

两个评判标准

判断一个人是否跟上了 AI 进程，看两点：

  1. 工具熟练度：是否熟练使用 Claude Code / Codex CLI / OpenCode 等编码 Agent？
  2. Token 消耗量：每月在编码上的 Token 使用量是否达到一定基线？（以亿 Token 为基准，包括输入、输出、缓存命中）

这两个指标回答同一个问题：你真的在”用”AI 解决问题，还是只在”聊”AI？

Vibe Coding 模式

我们的方案：不为学员讲知识，为学员提供”真实问题 + Vibe Coding 环境”。

不是”学完再做”，是做着学着。每一行 HTML、每一次 Agent 调用、每一个做完的产品，都在推高你的 Token 消耗——而 Token 消耗量本身就是最好的学习进度条。

4.7 多智能体协作

4.7.1 子智能体的本质：模型相同，身份不同

多智能体的核心秘密就一句：所有子 Agent 调的是同一个模型，区别在于 System Prompt + 工具权限 + 上下文窗口不同。

同一个 Claude Sonnet 4.8，给它三套配置：

Planner 子智能体：System Prompt 设为”你只做规划，不写代码”，工具只给文件读取权限，上下文只放产品需求文档
Coder 子智能体：System Prompt 设为”你只写代码，不做决策”，工具给终端和文件写入权限，上下文放规划文档+项目代码
Reviewer 子智能体：System Prompt 设为”你只审查代码，不改代码”，工具给文件读取和浏览器权限，上下文放代码 diff

模型完全一样，但三个 Agent 的行为完全不同。多智能体解决的不是”模型不够强”的问题，而是**”一个上下文窗口里既要规划、又要写代码、又要审查——脑子会混”**的问题。Planning 的思考会污染 Coding 的专注，Coding 的结果让 Reviewer 没法客观。拆开之后，每个 Agent 只干一件事，上下文干净。

在 Claude Code 中的实现：Skills 文件

Claude Code 用 Skills 机制承载子智能体。每个 Skill 文件 = 一个子智能体的”身份证”，包含三要素：人设（System Prompt）、权限（允许调哪些 MCP 工具）、领域知识（你擅长什么场景）。

项目目录结构：

主 Agent 遇到复杂任务 → 读取 planner.md → 以 Planner 身份规划 → 规划完成 → 上下文重置 → 读取 coder.md → 以 Coder 身份开发。每次切换都是一次上下文隔离 + 角色注入，不是同一窗口里硬切。

4.7.2 什么时候用多智能体

不是越多越好。Anthropic 明确指出：多 Agent = 3-10 倍 Token 消耗。只有单 Agent 真搞不定时才上
上下文隔离：不同任务需要不同上下文，混在一起互相污染。写代码的和写文档的分开
并行加速：任务可拆成独立子任务同时跑。16 个 Claude 并行编译 C 编译器
专业分工：不同角色需要不同的 Prompt 和工具。Planner 只管规划，Generator 只管实现
铁律：先跑通单 Agent → 确认瓶颈 → 再拆多 Agent，别一开始就搞多 Agent

4.7.3 三种协作模式

Orchestrator-Workers：一个调度者拆任务、分配、汇总。Worker 各干各的，互不干扰。Claude Code 的 SubAgent 走这条路
Peer-to-Peer：Agent 之间直接委托任务，各自领域按需协作。A2A 协议专为此设计，适合跨组织跨厂商
Pipeline：流水线式传递——Planner → Generator → Evaluator。每一步输出是下一步输入，质量逐级加码

4.7.4 关键机制

上下文隔离：每个 Agent 独立上下文窗口，互不可见，防止污染
任务拆分：Initializer Agent 拆功能清单 → 多 Coding Agent 各领一个功能，避免一次性全做
结果仲裁：Evaluator Agent 打分，不通过退回重做，防止劣质产出蒙混过关
文件交接：Agent 间通过文件系统（JSON/进度文件）通信，不靠对话。文件是结构化、可追踪、可断点恢复的

4.7.5 代价与决策

单 Agent：便宜、简单、够用大多数场景。先跑通单 Agent，确认真的搞不定（上下文撑爆、速度太慢、质量不可接受）再拆
多 Agent：3-10 倍 Token、架构更复杂、调试更难。收益是上下文隔离 + 并行加速 + 质量门控
决策原则：不是因为多 Agent 酷，是因为单 Agent 真的不够用

五、驾驭工程：95% 的功夫不在模型

5.1 驾驭工程是什么

问题是这样的：

GPT-5.5 能写诗、Claude Opus 能写代码、Gemini 能看懂视频。单论模型能力，它们已经超过大部分人类在特定任务上的表现。但当你真的想做一个能用的 Agent 产品——比如让 AI 持续 30 分钟帮你写项目——你会发现它问三句话就忘了开头、跑 10 步就迷路了、上下文越长越笨、偶尔还会乱删文件。

模型已经够强了。卡住的是「怎么让模型持续、稳定、安全地做事」。

2026 年 3 月 31 日，Claude Code npm v2.1.88 意外泄漏了 512,000 行 TypeScript 源码。分析结论：95% 的代码是 Harness（驾驭层），只有 5% 是 Agent 核心逻辑。

模型提供推理（发动机），Harness 提供控制、持久性、安全、可靠性（底盘、悬挂、刹车、方向盘）。模型换一代，能力强 20%；Harness 做对一次，效果翻倍。

驾驭工程的三层架构（C-A-R）：

Claude Code 源码将驾驭工程组织为三个正交的层级：

层级 回答的核心问题 源码锚点
Control（控制层） 谁说了算？Agent 能做什么、不能做什么？ types/permissions.ts — 五种权限模式；query.ts:554-558 — 退出机制；autoCompact.ts:70 — 熔断器
Runtime（运行时层） Agent 如何持续、稳定地跑下去？ query.ts:241,307 — async generator Loop；compact/ 服务 — 四层降级；compact/prompt.ts:354 — Protected Tail
Agency（代理层） Agent 能调什么工具、加载什么技能、怎么协作？ Tool.ts（792行）— 工具生命周期；SkillTool/prompt.ts:21 — 1% 预算；EnterPlanModeTool — 规划状态切换

三层缺一不可：Control 没做好 → Agent 越权搞破坏；Runtime 没做好 → 上下文越长越蠢；Agency 没做好 → 工具太多选不对。

5.2 心跳：Agent Loop — 模型天生只会一问一答，怎么让它持续多步自主执行？

问题是这样的：

5.3 记忆：上下文管理 — 跑着跑着就忘了，怎么办？

Agent 的记忆问题分三个层面：单次会话内对话太多（Token 雪球）、压缩把眼前的事也模糊了（丢失工作记忆）、会话结束全忘（没有长期记忆）。三层问题，三层解法。

病①：每一轮对话都塞进上下文，Token 雪球越滚越大，Agent 越跑越笨

Agent 跑一轮：用户消息 + LLM 回复 + 工具调用 + 工具结果。跑 10 轮：上下文里就有 10 份完整的工具结果。跑 50 轮：50 个 FileRead 结果堆在上下文里，大部分是重复读同一个文件。Agent 越跑越慢、越跑越贵、越跑越笨——因为有效信息被噪音淹没了。

药：四层渐进降级链路。便宜的先跑，贵的后跑。

为什么是「降级链路」而不是「单次压缩」？ 前三层零 API 调用，能省则省。只有前三层都不够时才启动 Autocompact——它调 LLM 最贵，但能把几十轮对话压成一段结构化摘要。好的 Harness 会让 Agent 尽可能在前三层解决问题，只在迫不得已时才启动第四层。

病②：Autocompact 把几十轮对话压成摘要——但「眼前正在做的事」不能也变成摘要

Autocompact 调 LLM 总结历史，省下了大量 Token。但如果把全部对话都交给 LLM 压缩，一个问题会出现：Agent 正在处理的任务——当前正在读的文件、刚发现的 bug、正在改的代码——也会被模糊化成一段摘要。就像你正在写代码，屏幕突然替换成一行「你在写代码」——细节全丢了。

药：Protected Tail — 最近 N 轮对话原文保留，不参与压缩。

compact/prompt.ts 第 354 行明确写道：“Recent messages are preserved verbatim.”

Protected Tail 就是 Agent 的「工作记忆」。 心理学里，工作记忆是你正在专注处理的、当前意识里活跃的信息——不是长期记忆（压缩后的摘要），也不是瞬时感知（刚收到的用户输入），而是「我正在处理什么」。这个设计让 Agent 在压缩历史后仍然保持工作连续性。

病③：会话结束全忘了——上周修的 bug、昨天定的命名规范，下次从头来过

上下文压缩管的是单个会话之内——跑 50 轮之后 Token 太多，压成摘要。但会话结束之后呢？下次开一个新会话，Agent 完全不记得上次做了什么、修了什么 bug、用户说过什么偏好。每次都从零开始。

药：文件系统作为跨会话记忆——不用存全部历史，只存关键事实。

Claude Code 的 Memory 系统有两层：

文件 机制 作用
CLAUDE.md 每轮循环自动重读 项目级记忆：代码风格、命名规范、架构约定
MEMORY.md Agent 自动写入关键事实 跨会话知识积累：「用户偏好 pnpm」「上次那个 bug 是 xx 导致的」

和上下文压缩的关系： 压缩管短期记忆（当前会话），Memory 管长期记忆（跨会话）。压缩通过 LLM 总结把几十轮对话压成摘要；Memory 通过文件系统把关键事实持久化到磁盘。两个系统互补——关键信息在压缩前就被写进了 MEMORY.md，不会因为压缩而丢失。

5.4 安全：刹车与护栏 — 能力越大，破坏力越大

Agent 能读文件、写文件、跑 shell 命令。能力越强，搞破坏的潜力越大。安全层解决四个问题：权限控制、硬性拦截、错误熔断、执行隔离。

病①：Agent 能写文件就能删库——越权怎么办？

药：五种权限模式 + deny 优先的权限管线。

每种模式下，还可以叠加细粒度权限规则（PermissionRule）：

权限检查的执行顺序：deny 优先。 先检查 deny 规则 → 再检查 allow 规则 → 都没匹配到 → 走当前模式的默认行为。这意味着一个 deny 规则可以覆盖所有 allow 规则——安全策略的最坏情况兜底。

工具生命周期的默认值是「不安全」。 源码的 TOOL_DEFAULTS 把 isConcurrencySafe 和 isReadOnly 的默认值都设为 false，checkPermissions 默认走完整权限管线。工具作者必须显式声明安全属性才能绕过检查。这是 Harness 的防御性设计——宁可多问一次，不要放过一个。

病②：Prompt 里写「绝对不要改生产环境」不管用——Agent 可能忘，需要硬拦截

Autocompact 会压缩对话历史。压缩后，用户在第 3 轮说的「金额字段单位是千元，千万别搞错」可能在摘要里变成了「用户提到过金额单位注意事项」——具体约束丢失了。更关键的是，Prompt 指令对 LLM 是软性的——模型可能因为上下文太长而忽略、遗忘。

有些约束必须硬性执行。比如「绝对不能连接生产数据库」「文件操作只能在 /workspace 下」——这些不能依赖模型「记住」，必须由系统强制执行。

药：Hook 在关键节点硬拦截，不依赖模型记忆力。

Claude Code 的 Hook 系统定义了 4 个生命周期事件：

Hook 触发时机 典型用途
UserPromptSubmit 用户消息发送给 LLM 之前 注入项目规范、检查用户输入
PreToolUse 工具执行前 硬拦截——检查命令是否安全、路径是否合法
PostToolUse 工具执行后 校验输出、记录日志、自动 commit
Stop Agent 停止时 自动保存状态、清理临时文件

关键机制：退出码 2 = 硬拦截。 Hook 返回非零值时，工具调用被阻断，返回值直接作为拒绝消息注入上下文。这不是「请模型自己判断要不要调这个工具」——是「系统不让调，模型你换个方式」。

Hook 解决了什么？ 把确定性规则从 Prompt 里搬到了代码里。Prompt 管「建议」，Hook 管「必须」。得物技术团队的实践：用 SessionStart hook 在每次 compact 后自动重新注入数据仓库字段约定——规范遵守率从 70-80% 提升到 95%+。

病③：API 崩了、连续 compact 失败——Agent 不能无限重试

Agent 调 LLM 可能遇到各种错误：prompt_too_long（上下文太长）、网络超时、API 限流。如果每次遇到就重试，无限循环——既浪费 API 额度，也消耗用户耐心。

药：分层错误处理 + 熔断器。

第一层：Reactive Compact（应急压缩）

5.5 能力：工具与技能 — Agent 的手和脚

Agent 只有大脑（LLM）不够，还需要手和脚来做事。但工具多了选不对，技能多了装不下，任务复杂了方向会错。三个问题，三个解法。

病①：15 种工具——怎么确保 Agent 选得对、参数传得对、不会死循环调同一个工具？

裸调 LLM API，模型只能输出文字。加了 Function Calling 之后，模型可以输出 {tool: "bash", command: "rm -rf /"}。如果直接执行，灾难。即使加了一道「等用户确认」，Agent Loop 也可能反复调同一个无效工具——读到空文件 → 再读 → 再读 → 死循环。

病②：Agent 装了 50 个 Skill，每个说明书塞进 System Prompt——上下文直接撑爆

5.6 协作：多 Agent 编排 — 一个脑子同时干所有活，会混

问题是这样的：

一个 Agent 承担所有角色——先规划架构、再写代码、再自己审查自己的代码——就会出现「裁判和运动员是同一个人」的问题。而且所有思考在同一个上下文窗口里，规划的细节会污染写代码的专注，写代码的结果让审查员无法客观。

解法：同一个模型，不同的 System Prompt + 工具权限 + 独立上下文窗口。

所有子 Agent 调的是同一个模型。区别只在于：System Prompt 定角色、工具列表定能力、上下文窗口定视野。

5.7 验证与可观测 — Agent 跑完了，做对了没？钱花哪了？

前面的章节都在讲「怎么让 Agent 跑起来」。但跑起来之后，还有两个问题没回答：跑的过程中发生了什么，我能看到吗？（可观测性）跑完的结果，是对的吗？（验证评估）。ETCLOVG 框架把这两层独立成 O 和 V——不是附属钩子，是控制平面的核心组件。

病①：Agent 跑完了——Token 烧了多少不知道，哪一步最费钱不知道，有没有死循环浪费也不知道

Agent 一次复杂任务可能调用几十次 LLM、上百次工具。如果不追踪，出了性能问题你连定位都定位不了。

可观测性的核心价值：不是「出了事再看」，而是「让每一次执行都可审计」。 好的 Harness 应该能回答：这次任务花了多少钱？哪一步最慢？有没有重复读同一个文件 20 次？子 Agent 各自消耗了多少 Token？

病②：长任务失败了——是模型推理错了、工具选错了、还是上下文丢了关键信息？没法定位

传统评估只看最终结果（「修好 bug 了吗？通过/不通过」）。但最终失败可能源于第 3 步的工具选错、第 7 步的上下文丢失——如果只给一个 end-to-end 分数，你根本不知道修哪里。

药：六层测试金字塔 + DAG 错误传播追踪。

Atlán 六层测试体系（Layer 0-5）：

关键数据：忽略了 Layer 0（数据验证）是 80-90% AI Agent 项目失败的根本原因。

AgentEval — DAG 结构化评估：

港大提出的 AgentEval 框架将 Agent 执行过程形式化为评估 DAG（有向无环图），每个节点是一个执行步骤，每条边表示步骤间的依赖关系。核心发现：

方案 失败检测召回率 根因准确率
仅端到端评估 0.41 N/A
平坦步骤评估 0.67 0.38
AgentEval（DAG） 0.89 0.72

63% 的步骤级失败源于上游错误传播，而非本地原因。 这意味着如果不追踪错误传播链，大部分失败你修错了地方。

Harness-Bench：换 Harness 比换模型更管用

CMU/耶鲁的 Harness-Bench 在 5,194 次执行中验证了约束绑定假说（Constraint-Binding Hypothesis）：

Agent 在复杂长任务中的可靠性，主要由 Harness 的工程质量决定，而非底层模型本身的推理能力。

同一模型，只换 Harness 配置（工具描述、上下文策略、权限规则），任务完成率可以差 30%+。这个幅度的提升远超模型迭代 2%-4% 的常规增益。

两个关键指标：

验证的核心理念：评估不解决任何问题——评估只告诉你问题在哪。 修的是 Harness：改工具描述、优化上下文策略、调整权限规则、加强 Hook 约束。评估 → 归因 → 修复 → 再评估，形成闭环。

5.8 公式与设计原则

回到开篇的公式，现在可以展开得更加具体：

乘法关系。 任何一个因子接近零，整体崩塌：

  • 裸调 API 只有聊天框能力 — 上下文质量、验证、记忆因子几乎为零
  • Claude Code 换一个 Harness，分数从 78% 腰斩到 42% — 同样模型，不同底盘
  • 砸模型不如砸 Harness — 模型是加数（+20%），Harness 是系数（×N）

五条设计铁律：

铁律 含义
不信任模型，信任系统 模型可能犯错——stop_reason 不可靠、可能忽略约束、可能选错工具。Harness 的职责不是让模型不犯错，而是让模型犯错时系统能兜住
失败关闭（Fail Closed） 不确定时，宁可拒绝也不冒险。deny 优先于 allow，默认值是不安全
机械强制优于文本规劝 Hook 拦截优于 Prompt 里写「千万别」、权限系统优于 System Prompt 里写「请遵守」
每遇到一个错误，就工程化一个解决方案 Mitchell Hashimoto 理念——不是修这一次，是让这类错误永远不再发生
成功应该沉默，失败才出声 反馈回路要对上下文窗口友好。正常执行不需要确认，异常才打断

Harness Engineering 的本质矛盾： 「赋予 Agent 充分能力」与「保证系统可预测、可控制」之间的平衡。不是什么新概念——是企业架构治理 + DevOps + RPA 实践在 AI Agent 时代的自然延伸。2026 年行业共识：模型的护城河正在趋同，真正的竞争壁垒正在向 Harness Engineering 转移。

AI 能帮你写代码，但产品上线不止是写代码。你需要知道一个网页从无到有经过哪些环节，才能在 Vibe Coding 时精准描述需求。

6.1 AI + 全栈：Vibe Coding 的核心优势

知道要什么

全栈知识不等于你要手写代码。它的价值在于：你能精准地告诉 AI “我要什么”。

不知道全栈时 知道全栈后
“帮我做一个网站” “用 React + Tailwind 做一个响应式首页，API 用 Express + PostgreSQL，部署到 Vercel”
AI 问”用什么认证方案？” — 你懵了 “用 JWT，access token 15 分钟过期，refresh token 7 天”

知道 AI 在干什么

AI 会生成 Dockerfile、GitHub Actions 配置、Nginx 配置——如果你完全不知道这些是什么，出了问题你连要搜什么关键词都不知道。

知道怎么验证

产品上线分三步：能跑 → 不崩 → 有人用。每一步都有对应的技术手段：

  • 能跑：本地测试 + Docker 本地跑一遍
  • 不崩：CI 自动测试 + 部署后监控
  • 有人用：域名解析成功 + HTTPS 正常 + 备案号挂好

6.2 互联网基础：从输入 URL 到看到网页

互联网怎么工作的

你在浏览器输入 www.example.com → 浏览器向服务器发起请求 → 服务器处理请求、查数据库 → 返回 HTML/CSS/JS → 浏览器渲染成你看到的页面。整个过程就是”请求-响应”循环。

HTTP / HTTPS

HTTP 是浏览器和服务器之间的通信协议。HTTPS = HTTP + 加密（SSL/TLS）。地址栏的小锁图标就代表 HTTPS。所有正式上线的产品必须用 HTTPS。

DNS 与域名

DNS 是”互联网的电话本”——你把域名（example.com）翻译成服务器 IP 地址（123.45.67.89）。没有 DNS，你只能背一长串数字访问网站。

浏览器渲染

浏览器收到 HTML/CSS/JS 后，解析成 DOM 树 → 计算样式 → 布局 → 绘制 → 你看到页面。理解这个流程，才知道”为什么页面加载慢””为什么样式没生效”。

托管（Hosting）

你的代码需要一个”家”——让全世界的人通过 URL 访问到。可以是云服务器（AWS/阿里云）、也可以是平台托管（Vercel/Netlify 一键部署）。

6.3 前端：用户看到什么

HTML — 网页骨架

HTML 定义网页的结构：标题、段落、图片、按钮。语义化标签（<header>、<nav>、<article>）让页面结构清晰、搜索引擎友好。

CSS — 网页皮肤

CSS 控制网页的外观：颜色、字体、间距、布局。Flexbox 和 Grid 是现代布局的基石，响应式设计（媒体查询）让页面在手机和平板电脑上都能正常显示。

JavaScript — 网页行为

HTML 是骨架，CSS 是皮肤，JavaScript 是肌肉——让页面动起来、响应用户操作。ES6+ 是现代标准，异步编程（Promise / async-await）是必须理解的核心概念。

TypeScript

JavaScript 的超集，加了类型系统。在变量定义时就声明”这个变量是字符串还是数字”，避免运行时类型错误。Vibe Coding 时代，AI 会大量使用 TypeScript。

React（前端框架三选一：React / Vue / Angular）

React 是目前最主流的前端框架。核心概念：组件化——把页面拆成独立的、可复用的模块，像乐高一样组装。AI 写 React 代码非常熟练。

Tailwind CSS（CSS 框架）

不用手写 CSS，直接在 HTML 里用类名描述样式（class="text-red-500 font-bold"）。AI 极其擅长 Tailwind——描述”我要一个红色加粗的标题”比手写 CSS 代码快十倍。

npm（包管理器）

JavaScript 的”应用商店”。你需要的功能大概率有人写好了——npm install 一行命令装上就能用。node_modules 文件夹不要提交到 Git（加到 .gitignore）。

6.4 后端：服务器在干什么

Node.js（后端运行时）

让 JavaScript 脱离浏览器，在服务器上运行。配合 Express 或 Fastify 框架，几行代码就能启动一个 Web 服务器。AI 写 Node.js 服务器的能力非常成熟。

RESTful API

前后端通信的”约定语言”：

方法 操作 例子
GET 读取 获取用户列表
POST 创建 新增一个用户
PUT 更新 修改用户信息
DELETE 删除 删除一个用户

API 返回的数据格式通常是 JSON——人可读、机器可解析。

认证：JWT / OAuth

  • JWT（JSON Web Token）：登录后服务器发给你一个”令牌”，后续请求带上令牌证明你是谁。像一个电子工牌。
  • OAuth 2.0：”用微信/Google 账号登录”就是 OAuth。用户不需要在你的网站注册新账号。

中间件

请求到达服务器后、到达最终处理函数之前，中间会经过多个”关卡”——日志记录、权限检查、速率限制——每个关卡就是一个中间件。

6.5 数据库：数据存哪里

SQL 关系型数据库（PostgreSQL / MySQL）

数据存在”表格”里，表格之间通过外键关联。适合数据结构固定、需要复杂查询的场景：用户系统、订单系统、账本。

核心概念：表（Table）、行（Row）、索引（Index）、事务（Transaction）、SQL 查询语言。

NoSQL（MongoDB）

数据存在”文档”（JSON）里，结构灵活。适合数据结构多变、需要快速迭代的场景：日志存储、用户偏好设置、内容管理。

Redis（缓存）

内存数据库，极快。常用场景：缓存热门数据（避免反复查数据库）、会话存储（用户登录状态）、排行榜（实时排序）。

ORM（Prisma / TypeORM）

不用手写 SQL，用 JavaScript 代码操作数据库。Prisma 是目前最主流的 Node.js ORM——定义数据模型 → 自动生成类型安全的查询代码。AI 写 Prisma 代码非常顺手。

什么时候用哪种

场景 推荐
用户、订单、账本 PostgreSQL
内容管理、灵活配置 MongoDB
缓存、会话、排行榜 Redis

6.6 版本管理与 CI/CD：代码怎么管、怎么自动上线

Git 核心操作

  • clone：把远程仓库拉到本地
  • commit：保存一次修改快照
  • push：把本地修改推到远程
  • pull：拉取远程的最新修改
  • branch：分支——不干扰主线的独立工作空间

GitHub 工作流

PR（Pull Request）是团队协作的核心机制——合并前让别人审查你的代码。

.gitignore

告诉 Git “这些文件不要跟踪”。必加：node_modules/、.env（含 API Key）、构建产物（dist/、build/）。

CI/CD（持续集成 / 持续部署）

  • CI（持续集成）：每次 push 代码，自动跑测试，确保没搞坏别的地方
  • CD（持续部署）：测试通过后，自动部署到服务器/平台

GitHub Actions 是最主流的 CI/CD 工具——在仓库里写一个 YAML 配置文件，push 代码后自动触发。Vibe Coding 时代，AI 能帮你写这个配置文件。

6.7 部署上线：让全世界看到

Docker（容器化）

把应用和它的所有依赖（操作系统、运行时、库）打包成一个”集装箱”，到任何服务器上都能原样运行。解决”我电脑上能跑，服务器上不行”的经典问题。

Dockerfile 定义怎么打包 → docker-compose 编排多个容器（前端+后端+数据库）→ 一条命令全部启动。

云服务器

服务商 一句话
阿里云 / 腾讯云 国内首选，ICP 备案方便
AWS / GCP / Azure 国际主流
Vercel / Netlify 前端一键部署，免费额度够用

新手入门推荐：轻量云服务器（1核2G，300-500元/年）。

Nginx（Web 服务器）

反向代理——外面来的请求先到 Nginx，Nginx 再转发给内部的 Node.js 应用。同时处理静态文件（图片/CSS/JS）、HTTPS 证书、负载均衡。

环境变量

开发环境的配置（本地数据库）和生产环境的配置（线上数据库）不一样。通过环境变量（.env 文件）区分，避免把开发配置带到线上。.env 必须加到 .gitignore。

6.8 域名与备案：在中国上线的合规链路

域名注册

在阿里云万网、腾讯云 DNSPod 注册。.com 约 50-80 元/年，.cn 约 30-50 元/年。注册后必须完成实名认证，否则域名无法解析。

DNS 解析

在域名注册商后台添加 A 记录：把域名指向服务器 IP 地址。@ 代表主域名，www 代表带 www 的子域名。解析生效通常需要 10 分钟到 24 小时。

ICP 备案（工信部）

国内服务器建站必须备案。 流程：

备案期间网站必须关闭或显示”备案中”。备案号获取后必须悬挂在网站底部。

公安备案

ICP 备案通过后 30 日内，登录「全国互联网安全管理服务平台」完成公安备案。获取”公网安备”编号，同样挂在网站底部。

6.9 安全与测试：让产品可信、可靠

HTTPS / SSL 证书

Let’s Encrypt 提供免费 SSL 证书，宝塔面板/Certbot 一键申请。配置 Nginx 强制 HTTP → HTTPS 跳转。没有 HTTPS 的网站，浏览器会标”不安全”。

OWASP Top 10（基础安全）

最常见的安全漏洞：

  • XSS（跨站脚本）：攻击者在你的网页注入恶意脚本 → 对所有用户输入做转义
  • SQL 注入：攻击者在输入框拼接 SQL 语句偷数据 → 用参数化查询或 ORM
  • CSRF（跨站请求伪造）：攻击者诱导用户执行非本意操作 → 加 CSRF Token

AI 写的代码默认会注意这些问题，但你需要知道这些概念存在。

密钥管理

API Key、数据库密码、JWT 密钥——全部放在环境变量（.env），永远不要提交到代码仓库。一旦泄露，立即在厂商后台吊销并重新生成。

测试

类型 做什么 工具
单元测试 测一个函数对不对 Jest, Vitest
集成测试 测多个模块一起工作对不对 Supertest
E2E 测试 模拟真实用户操作 Playwright, Cypress

AI 能帮你写测试，但你需要知道”该测什么”——测核心功能、测边界情况、测用户最常走的路径。

七、具身智能：AI 从数字世界走向物理世界

具身智能 = 让 AI 拥有身体，能在物理世界里感知、思考、行动。你日常用的 ChatGPT 只能”回话”，具身智能能”走过去拿起杯子”。

7.1 三个核心要素

大脑

VLA（视觉-语言-动作）大模型驱动的高层推理、任务分解与决策。理解”把桌上的苹果拿给我”，拆成走过去→找到苹果→伸手→抓取→递给你。

身体

传感器（摄像头、激光雷达、触觉电子皮肤）+ 执行器（灵巧手、电机、关节）。大脑想好了，身体去执行。

环境

物理世界中的”感知→行动→反馈”闭环。机器人伸手碰杯子——杯子动了——大脑收到反馈：没抓稳，调整力度再来一次。

感知层：视觉感知、触觉感知、SLAM 定位、多模态融合。让机器人知道前面有什么、自己在哪、摸到了什么
