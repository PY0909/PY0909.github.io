1.2 大模型的核心概念

Token 与上下义窗口 Tokon是计价和阅读单位，中文约 0.5 字/Token；上下文窗口是模型一次能看到的Token上限。窗口大 ≠ 要用满，历史会被重复计费
流式输出（Streaming） AI 逐字输出的底层机制:服务器通过 SSE 一个字一个字推送，不等全生成完。非流式=等几秒一次性出全文
Temperature 控制输出的随机性。温度越低越稳定(写代码用 0)，温度越高越发散(写诗用1.2)，日常明天用 0.7
TOP-P 核采样，限制候选词的概率范围。和 Temperature 类似，通常二选一即可
System Pramot 设定 AI 的人设和行为边界，对话开始时发送。与User Prompt 分工（System Promot 定规则，User Prompt 提问题）
结构化输出 **强制 AI 以 JSON 等固定格式返回，对接程序或批量数据处理时必备
模型局限 幻觉：自信编造不存在的事实；知识截止：训练数据有日期限制；偏见与越狱：安全策略可能被统过
选型与成本 简单任务用便宣的。写代码用Cleude，中文优先国内模型。Benchmarks(MMLU/HumanEvel/Arena)衡量模型能力

1.3 Prompt工程

ROLE 框架 R=角色，〇=输出格式，L=限制，E=示例。角色越具体输出越精准，好 Prompt 是改出来的：写→看输出→改→再试
Few-shot 给 2-3 个范例再提问，模型会模仿格式和语气，输出质量大幅提升
Zero-shoto 不给范例直接问，省事但效果弱于 Few-shot。简单任务可用，复杂任务优先 Few-shot
思维链(CoT) 加一句”请一步步分析再给结论”，强制模型展示推理过程，避免跳逻辑直接猜答案
结构化模板 用 Markdown 分块写清角色、任务、输出格式、约束条件，复杂任务不结构化易遗漏要求
工具描述工程 Agent 配置中，工具的描述用词直接影响调用准确率，描述越精确效果越好
常用模式 说要什么比说不要什么好，给范例比解释规则好，复杂任务拆多轮比塞一条长 Prompt 好
常见反模式 一次塞太多要求导致质量下降，Prompt 过于模糊输出不可预测，用否定句反而强化负面

2.2 API Key 与 Token

一级分类 细分条目 详细说明
API Key 是什么 身份令牌定义 调用 AI 厂商服务的身份凭证，请求携带 Key，厂商通过 Key 识别账户并扣费
API Key 是什么 完整调用扣费流程 本地终端发起请求 → 服务端读取 API Key → 校验账户余额 → 余额充足则运行模型 → 按照消耗 Token 扣费
怎么拿到 Key DeepSeek 平台 官网：platform.deepseek.com操作流程：注册账号 → 进入 API Keys 页面 → 创建密钥 → 复制保存 → 最低充值 10 元即可调用；其余厂商平台操作逻辑一致
怎么拿到 Key 阿里通义千问（DashScope） 官网：dashscope.aliyun.com
怎么拿到 Key 字节豆包（火山引擎） 控制台地址：console.volcengine.com
怎么拿到 Key Google Gemini 平台地址：aistudio.google.com
怎么用 终端环境变量配置（Zsh） 写入配置文件 ~/.zshrc，示例代码：export DEEPSEEK_API_KEY="sk-xxx"；保存后执行 source ~/.zshrc 生效；Claude Code、Aider 等 CLI 工具会自动读取环境变量
绝对不能做的事 禁止硬编码 Key 进代码文件 代码提交至 GitHub 后，平台自动化扫描脚本会快速窃取密钥，被盗刷产生高额账单
绝对不能做的事 禁止截图密钥发社交平台 API Key 完全暴露，任何人获取后都能消耗你的账户额度
绝对不能做的事 禁止将 Key 写在前端代码内 浏览器 F12 开发者工具可直接查看，密钥完全裸奔泄露
绝对不能做的事 禁止多人共用同一 API Key 出现超额消耗、违规调用时无法定位责任人，额度消耗溯源困难
绝对不能做的事 安全铁律 API Key 仅存放于本地环境变量，严禁提交至任何代码仓库（Git/GitHub/Gitee 等）
Token 计费 Token 基础概念 Token 是 AI 模型计价单位，不等于纯文字字数；中文约 0.5 字 / Token，英文约 0.75 单词 / Token；输入 Token（用户提问）单价更低，输出 Token（模型回复）价格贵 2~5 倍
Token 计费 产品侧成本估算公式 单次调用成本 = 输入 Token × 输入单价 + 输出 Token × 输出单价月度预估成本 = 30 × 日均调用量 × 单次调用成本监控指标推荐使用 P95 百分位，不使用平均值：100 次调用数据排序取第 95 位数值，覆盖 95% 业务场景成本关键变量：日活跃用户 × 人均调用次数 × 单次 Token 消耗量；上线前压测一周获取基准数据
Token 计费 P95 百分位理论依据 参考 Google SRE 权威手册《Monitoring Distributed Systems》，书中明确：监控系统延迟、资源消耗需使用百分位而非平均值https://sre.google/sre-book/monitoring-distributed-systems/
Token 计费 模型选型成本逻辑 调用成本高低由业务任务难度决定，简单场景选用轻量低价模型，复杂推理 / 代码场景选用旗舰高价模型

三、RAG 与知识增强方案

3.1 为什么需要RAG：模型知道什么、能读什么

知识的局限：

局限类型 详细说明 影响与补充说明
知识截止 模型训练数据集存在固定截止日期，无法知晓截止时间之后发生的事件、新闻、新规范、新技术 想要获取实时信息必须搭配联网检索工具（Search/RAG）
模型幻觉 大模型本质是预测下一个文字 Token，并非查询真实数据库，会自信输出不存在、错误的事实、文献、数据 涉及严谨业务场景必须增加引用溯源、检索校验步骤
私有知识盲区 模型训练数据仅为公开互联网数据，完全无法获取企业内部文档、个人笔记、私有项目资料、内部业务流程 私有化知识库、RAG 向量库是解决该问题的标准方案
专业深度不足 通用大模型覆盖全行业基础常识，但在医疗、法律、工业、底层开发等垂直细分领域专业深度不足 需要投喂行业专业文献、领域微调、垂直行业知识库增强

格式的局限：

分类 内容详情 关键限制 / 处理方案
纯文本模型原生支持格式 Markdown、JSON、HTML、txt 纯文本、各类代码文件、CSV 表格 可直接读取解析，无需额外预处理
纯文本模型无法原生读取格式 PDF、Word (docx)、Excel (xlsx)、图片、音频、扫描件 必须先做 OCR 文字提取、格式转文本预处理才能投喂模型
多模态视觉模型读图原理 将图片像素编码为 Token，和文本 Token 混合运算理解，并非真正 “打开文件解析” 多页扫描 PDF、长图文会瞬间耗尽 Token 限额，成本极高、易超限报错
RAG 核心作用（解决上述格式 + 知识双重局限） 完整预处理链路：各类文档统一转换为 Markdown → 文本切块分片 → 文本向量化嵌入 → 存入向量知识库 1. 统一兼容所有文件格式2. 规避超长文件 Token 爆炸3. 注入私有专属知识，消除知识盲区

四、智能体

4.1 智能体是什么：从 LLM 到 Agent 的跨越

一、Agent 完整定义公式

  1. LLM 大脑：负责思考、推理、理解人类指令，是核心决策主体；
  2. Memory 记忆：短期对话上下文、长期历史任务记录，记住之前做过的步骤、拿到的结果；
  3. Planning 规划：把复杂大任务拆解成多步子步骤，制定执行顺序；
  4. Tool Use 工具调用：可以主动调用外部能力（联网搜索、读写文件、API、代码解释器、向量知识库等）；
  5. Skills 技能：封装好的可复用能力（数据分析、文档解析、代码生成、报表导出等）。

二、原生 LLM vs AI Agent 核心区别对照表

对比维度 单纯 LLM（普通大模型对话） AI Agent（智能体）
能力边界 仅依赖训练时录入的静态知识，无外部实时信息 训练知识 + 外部工具实时获取信息、本地文件、业务接口数据
行为模式 单次一轮对话，一问一答，不会主动多步骤执行 自主循环多步执行，自动拆解任务、反复调用工具直到完成目标
工具调用能力 ❌ 不能主动调用工具，只能纯文字输出 ✅ 主动搜索、读写本地文件、调用 API、运行代码、操作知识库
自我纠错能力 ❌ 输出错误无法自查、修正 ✅ 执行→校验结果→发现错误→修正参数→重新执行，闭环纠错
典型适用场景 日常聊天、短文写作、翻译、简单问答 完整项目搭建、行业深度调研、自动化工作流、复杂业务流程、批量文档处理

三、Agent 核心运行骨架：Agent Loop 循环（ReAct 实现）

1. 通用三层循环骨架（所有智能体通用）

  1. Observe 观察

    读取当前环境、工具返回结果、历史记忆、用户需求，拿到全部已知信息；

  2. Think 思考（Planning 规划）

    分析现状、判断信息是否充足、拆解下一步要做的动作、判断要不要调用工具；

  3. Act 行动（Tool Use 工具执行）

    调用对应工具执行操作（联网、查知识库、运行代码、读取文档）；

  4. 循环闭环：行动完成后回到「观察」，读取工具返回结果，再次思考，重复直到任务全部完成。

2. ReAct：最主流的 Agent 循环实现方案

ReAct 是行业标准落地框架，一一对应循环骨架：

  • Observe（观察环境） → 对应 ReAct：观察工具返回内容
  • Think（推理规划 Reasoning） → 分析现有信息，确定下一步动作
  • Act（行动 Acting） → 发起工具调用
  • 循环：观察返回结果 → 重新推理 → 再次行动，直至任务结束

四、Agent 综合能力计算公式

  1. 模型自身能力：LLM 的逻辑推理、理解、规划水平（GPT-5.5、Claude Opus、豆包 V4.5 等）；
  2. 外部接口广度：能调用多少工具 —— 向量知识库、代码执行、文件读写、业务 API、联网搜索、表格处理、OCR 文档解析等；工具越多，能处理的复杂场景越多；
  3. 工程驾驭质量：记忆管理、循环终止条件、错误重试、工具参数校验、多步骤调度代码的稳定性，工程差会出现无限循环、乱调用工具、任务中断。

五、通俗落地举例（看懂 Agent 和普通 LLM 的差别）

例子需求：帮我整理公司所有合同 PDF，统计每个项目金额，输出 Excel 报表

  1. 普通 LLM 做不了

    只会告诉你 “我不能读取本地文件，无法统计”，仅能做文字理论说明，没有文件读写、表格生成工具能力，不会分步处理。

  2. Agent 完整自动执行流程（ReAct 循环）

  3. 观察：用户需求 + 本地文件夹路径记忆

  4. 思考：任务拆分为「读取 PDF→解析合同文本→提取项目金额→汇总数据→生成 Excel」

  5. 行动 1：调用文档解析工具，批量读取所有合同 PDF（MinerU/Docling）

  6. 观察：拿到所有合同文字，发现部分扫描件文字识别不全

  7. 思考：需要补充 OCR 重新识别扫描 PDF

  8. 行动 2：调用 OCR 工具重新解析扫描件，补全金额数据

  9. 观察：全部金额提取完成

  10. 思考：需要整理结构化表格

  11. 行动 3：调用代码工具运行 Python，生成 Excel 报表保存到本地

  12. 观察：Excel 生成成功，信息完整，任务终止，返回文件路径给用户

全程自主循环、自动纠错、多工具串联，无需人工分步指令。

1. 大脑（LLM）

概念

智能体的思考核心，也就是大语言模型，所有判断、推理、理解、文字生成全部依靠它。

在循环里的作用

对应 ReAct 的 Think（推理 Reasoning） 阶段：

  1. 读取用户需求 + 记忆里的历史记录 + 工具返回结果
  2. 分析当前信息是否充足，判断下一步要做什么
  3. 输出决策：调用哪个工具、怎么拆解任务、是否结束任务
落地用法
  • 产品：豆包大模型、GPT、Claude、Gemini 作为智能体底层大脑
  • 开发：LangGraph/LlamaIndex 接入任意主流 LLM 作为推理内核

2. 记忆（Memory）

概念

持久化存储模块，分为短期对话记忆、长期任务记忆，跨循环不会丢失，每一轮思考都会读取历史记录。

在循环里的作用

全局配套模块，不单独属于某一步，每一次 Think 都会读取全部记忆，实现连贯多轮任务：

  • 短期记忆：当前对话内每一步工具返回结果、中间推理过程
  • 长期记忆：永久保存专属人设、私有知识库、历史完整任务记录
落地用法
  • 低代码（豆包智能体 / Dify）：开启「长期记忆」，智能体永久记住业务流程、历史问答
  • 代码开发：向量库 / 数据库存储记忆，支持跨会话调取历史任务

3. 规划（Planning）

概念

任务拆解能力，由 LLM 大脑实现全局统筹，复杂任务自动拆分有序步骤，避免混乱执行。

在循环里的作用

属于 Think 环节，全局视角统筹全局：

拿到复杂目标后，先输出完整执行顺序，循环中动态修正计划（工具执行失败会自动调整步骤）

落地用法
  1. 简单规划：固定分步指令（上传文档→提取数据→生成表格）
  2. 动态规划：Multi-Hop、Corrective RAG，根据工具结果实时调整检索 / 执行步骤

4. 工具（Tool Use）

概念

智能体和外部世界交互的 “手脚”，是获取外部信息、执行操作的唯一渠道。

在循环里的作用

对应 ReAct 的 Act（行动 Acting） 阶段：

思考完成后，根据决策调用对应工具执行操作，执行完返回结果，回到 Observe 观察环节。

常见工具类型

文档解析工具、向量知识库检索、联网搜索、代码解释器、Excel 读写、业务 API、OCR 识别

5. Skills（技能）

概念

把「规划逻辑 + 多工具调用流程」打包封装成一套完整可复用技能，是预制的标准化工作流。

在循环里的作用

跨组件整合：内置一套固定的 Think 思考逻辑 + 多 Tool 连续调用流程，一次触发自动跑完完整业务。

落地例子
  • 法务审查 Skill：上传 PDF 合同 → OCR 解析 → 检索法条知识库 → 提取风险条款 → 生成风险汇总表
  • 研发文档 Skill：读取代码仓库 → 检索技术文档 → 生成接口说明文档
落地用法

豆包智能体、Dify 平台直接创建自定义技能，保存后重复调用，不用每次重新写流程指令。

4.3 经典范式：Agent 怎么“想”和“做”

范式名称 核心逻辑 适用场景
ReAct（边想边做） 一轮一轮循环：思考→行动→观察，边执行边动态调整思路 任务路径模糊、信息未知，需要边搜边推进
Plan-and-Solve（先画地图，再走路） 第一步完整拆分全部子任务规划清单，再按顺序统一执行，最后收尾校验 任务步骤固定清晰、已知完整流程，一次性规划后高效执行
Reflection（做完回头看，自我纠错） 先生成初稿，再多轮自我批判反思，找出缺陷迭代修正，多层打磨提升质量 对严谨度、事实准确性、文章质量要求极高的场景

一、ReAct（边想边做）

核心原理

循环闭环：思考(Think) → 行动(Act) → 观察(Observe)，一轮一轮递进，每一步根据上一轮拿到的结果实时调整下一步方案，不用提前写完整计划。

案例（写 AI 行业简报）

  1. 第 1 轮

    思考：要写行业简报，先搜 2026 年 6 月 AI 行业动态；

    行动：调用搜索工具，关键词 AI 行业动态 2026年6月；

    观察：返回 8 条新闻链接 + 摘要。

  2. 第 2 轮

    思考：现有新闻只有产业、融资、政策，缺少技术突破内容，需要补充搜索；

    行动：搜索 AI 技术突破 2026；

    观察：新增 5 条技术新闻。

  3. 第 3 轮

    思考：12 条信息覆盖全部维度，素材充足，直接按「标题 - 综述 - 分述 - 展望」写简报；

    行动：分段生成简报初稿；

    观察：简报草稿完成。

  4. 第 4 轮

    思考：核对事实、来源、篇幅格式；

    行动：逐条核对、补充引用、调整排版；

    观察：终版完成，任务结束。

优缺点
  • 优点：灵活自适应，信息不全时自动补充检索，适配未知复杂问题；
  • 缺点：多轮调用工具，执行轮次多，耗时更长；
适用场景

任务路径不确定、需要边做边搜集信息（行业调研、开放式问答、多跳 RAG）。

二、Plan-and-Solve（先规划，再统一执行）

核心原理

分三大阶段：规划 Plan → 执行 Solve → 收尾校验

  1. 规划阶段：一次性拆解完整子任务清单；
  2. 执行阶段：严格按规划顺序逐个完成所有子任务；
  3. 收尾阶段：统一检查全部任务是否完成，再输出最终结果。
案例（写 AI 行业简报）
阶段 1 规划 Plan，一次性拆分全部 7 个子任务
  1. 搜集产业动态（大模型新品、产品更新）
  2. 搜集资本市场信息（融资、IPO、估值）
  3. 搜集政策监管动态
  4. 搜集技术突破（论文、开源项目）
  5. 交叉验证全部事实来源
  6. 撰写完整简报：综述→产业→资本→政策→技术→展望
  7. 排版、添加来源引用
阶段 2 执行 Solve

严格按上面 1~7 顺序逐个完成，做完一个维度再下一个，全部素材搜集完毕后再统一写稿、排版。

阶段 3 收尾

核对 7 项子任务全部完成，无遗漏后输出终稿。

优缺点
  • 优点：全局一次性规划，执行路径清晰，减少重复思考，效率更高；
  • 缺点：前期对任务认知不足时，容易规划出错，后续无法灵活调整；
适用场景

任务流程清晰、步骤固定、提前能预判全部环节（标准化报表、固定办公流程、已知业务流程）。

三、Reflection（反思自省，多轮纠错打磨）

核心原理
  1. 先用 ReAct/Plan-Solve 产出第一版初稿；
  2. 模型以第三方视角自我批判，逐条列出内容缺陷；
  3. 根据反思结果修正内容，生成新版本；
  4. 可重复多轮反思迭代，直到无明显问题。
案例（写 AI 行业简报）

  1. 第 1 轮 产出初稿

    使用 ReAct 或 Plan-Solve 生成完整简报第一版。

  2. 第 2 轮 Reflection 自我审查

    自主找出 4 类问题：

    ① 产业只覆盖海外，缺少国内行业视角；

    ② 融资数据引用二手网页，缺少一手官方公告，事实不可靠；

    ③ 专业术语过多，普通读者可读性差；

    ④ 结尾展望仓促，缺少明确行业趋势判断。

  3. 第 3 轮 基于反思修正

    补充国内动态、替换一手来源、简化专业术语、重写结尾展望，产出第二版简报。

  4. 第 4 轮 二次反思微调

    发现段落顺序不合理，调整板块排序，得到最终定稿。

优缺点
  • 优点：大幅降低幻觉、提升严谨度、优化文字质量，适合高要求专业输出；
  • 缺点：多轮迭代，资源消耗、耗时翻倍；
适用场景

法律合同、行业深度报告、学术文案、对外正式文稿、对事实严谨性要求极高的场景。

超大、超复杂综合任务 Plan + ReAct 混合 先用 Plan 搭建全局框架，每个子任务内部再用 ReAct 灵活执行

落地混合用法

复杂长任务通用最优搭配：

  1. 先用 Plan 拆解全部大的阶段，搭建整体骨架；
  2. 每个细分子任务内部，使用 ReAct 循环搜集资料、分步完成；
  3. 全部内容写完后，开启多轮 Reflection 自我校验修正，产出高质量终稿。

4.6 Vibe Coding：AI 时代的核心能力

一、什么是 Vibe Coding

1. 核心定义

Vibe Coding 是纯自然语言驱动的 AI 全流程开发模式，不用手动写大量代码、不用精通语法，只靠口语化描述需求，让编码智能体（Claude Code / Cursor / OpenCode）自动完成整套项目开发，全程靠 “氛围、需求体感” 驱动开发，故名 Vibe（氛围 / 体感）Coding。

和传统写代码的区别：

  • 传统编码：人先画架构、手写每一行代码、手动调试；
  • Vibe Coding：人只说业务场景 / 难题，AI 自主搭架构、写代码、排错、实现完整可运行产品。
2. 底层核心逻辑
  • Token 上涨：每一轮需求、开发、反馈、修改都会产生大量上下文 Token，大量真实工程实操让模型积累实战经验；
  • 能力生长：大量真实项目迭代训练，AI 的工程、排错、产品落地能力持续提升。
3. 常用工具
  1. Cursor（最主流）：内置 Claude Code，开箱即用 Vibe Coding
  2. Claude Code：Anthropic 原生编码 Agent，MCP 生态完善
  3. OpenCode：开源免费，兼容 70 + 大模型
  4. Codex CLI：OpenAI 官方命令行编码工具

二、完整怎么做 Vibe Coding（分步实操）

步骤 1：抛出完整真实场景 / 需求

不要写技术参数，只用大白话描述真实难题、使用场景、目标用户。

示例需求：

做一个企业合同 RAG 智能体工具：支持上传 PDF 合同、自动提取金额与风险条款、检索内部合同知识库、输出风险汇总 Excel，给公司法务日常批量审查使用。

步骤 2：启动 Vibe Coding，AI 全自动产出完整可运行产品

打开 Cursor / Claude Code，粘贴需求，AI 自动完成全流程开发：

  1. 自主拆解项目架构、前后端、依赖包、文件目录；

  2. 自动编写全部代码、工具调用逻辑、RAG 预处理、Excel 导出功能；

  3. 自动调试报错、修复兼容性问题；

  4. 输出完整本地可运行工程（前端页面 + 后端接口 + 启动脚本）。

    全程不用你写一行代码，仅靠自然语言交互。

步骤 3：提交成品，收集反馈

AI 输出可运行项目后，本地部署运行，把使用中的问题、bug、功能缺失整理成反馈丢给 AI：

例：

  1. 扫描件 PDF 识别乱码；
  2. Excel 只能导出单份合同，不支持批量汇总；
  3. 检索时关键词匹配不准。
步骤 4：反馈驱动迭代优化

把反馈丢回编码 Agent，AI 自动修改对应代码、新增功能、修复缺陷，循环「提交→反馈→迭代」，直到产品满足业务需求。

步骤 5：长期迭代，沉淀能力

多轮开发 + 反馈会产生海量上下文 Token，AI 在大量真实工程里积累落地经验，后续同类项目开发速度、准确率持续提升。

4.7 多智能体协作（Multi-Agent）

4.7.1 子智能体的本质：同模型、不同角色分工

底层共用同一个大模型，靠专属提示词 Prompt、工具权限、独立上下文区分角色，互不干扰。

三类标准编码子智能体（Claude Code 标准分工）

子智能体角色 专属 System Prompt 定位 开放工具权限 专属上下文内容 Claude Code 配置文件
Planner 规划智能体 只做项目拆解规划，不写一行代码 仅文件读取权限，禁止写入 / 运行终端 仅产品需求文档，看不到代码 .claude/skills/planner.md
Coder 编码智能体 只执行编码实现，不做整体决策 文件读写 + 终端运行完整权限 规划文档 + 项目全部代码 .claude/skills/coder.md
Reviewer 审查智能体 只校验代码缺陷，不修改代码 文件读取 + 浏览器预览权限 代码变更 diff 对比文件 .claude/skills/reviewer.md
落地实现

在 Claude Code 中，通过项目目录 .claude/skills/ 下单独 md 文件定义每个子智能体的人设、权限、能力，一键调度启用。

4.7.2 多智能体适用场景（什么时候该拆多 Agent）

铁律：优先单 Agent 跑通，出现瓶颈再拆分多 Agent；不要一上来就做多智能体

多 Agent 会带来 3~10 倍 Token 消耗，仅满足以下场景才值得使用：

  1. 上下文污染隔离

    规划、编码、测试、文档任务混杂在同一个上下文会互相干扰；不同角色独立窗口，互不干扰。

    例：写代码的 Agent 和写产品说明书的 Agent 分开，代码不会污染文档思路。

  2. 并行加速任务

    任务可拆分为完全独立子任务，多个 Agent 同时并行执行，大幅缩短耗时。

    例：16 个 Claude 并行编译 C 语言大型编译器、同时开发多个独立功能模块。

  3. 专业角色分工

    不同环节需要专属 Prompt、差异化工具权限，单一 Agent 无法兼顾多重身份。

    例：规划者只做架构，编码者只写代码，审查者只找 bug，各司其职。

  4. 单 Agent 能力瓶颈

    超长项目、超大上下文、复杂多环节流水线，单个 Agent 上下文窗口撑爆、输出质量失控。

4.7.3 三种标准协作架构模式

1. Orchestrator-Worker 调度者 - 工人（Claude Code SubAgent 默认方案）

  • 逻辑：1 个总调度 Orchestrator 负责拆解任务、分配子任务、汇总全部结果；多个 Worker 子智能体独立干活，互不干扰。
  • 适用：大型工程项目、Vibe Coding 完整产品开发。

2. Peer-to-Peer 对等互通（A2A 协议支撑）

  • 逻辑：Agent 之间无上下级，可互相直接委托任务，跨厂商、跨系统自由协作。
  • 配套技术：A2A（Agent-to-Agent）通信协议。
  • 适用：跨企业、跨工具生态多智能体协同。

3. Pipeline 流水线串行

  • 逻辑：任务线性传递，上一个 Agent 输出直接作为下一个 Agent 输入，逐级提升质量。
  • 链路示例：Planner规划 → Coder编码 → Reviewer评审
  • 适用：标准化固定流程（代码开发、报告撰写、合同审查流水线）。

4.7.4 多 Agent 运行关键底层机制

1、上下文完全隔离

每个子智能体拥有独立上下文窗口，看不到其他 Agent 的对话、内容，杜绝信息混杂污染。

2、自动任务拆分

由初始化 Agent 拆解完整需求为细分功能清单，分给多个编码 Agent 各自认领模块，避免单次任务过重。

3、结果仲裁校验

设置 Evaluator 评审智能体，统一给所有产出打分，不合格直接退回对应 Agent 重做，拦截劣质输出。

4、文件系统标准化通信

Agent 之间不靠对话传递数据，统一读写本地结构化文件（JSON、进度文档、diff 日志）；

优势：内容可追溯、支持断点续跑、结构清晰稳定。

4.7.5 成本、取舍、落地决策原则

两种方案对比：

方案 优势 短板
单 Agent 成本低、架构简单、调试容易、绝大多数轻量场景够用 长复杂任务上下文超限、多角色混杂思路混乱、无法并行提速
多 Agent 上下文隔离、多任务并行加速、专业分工质量可控、长任务不超限 Token 消耗提升 3~10 倍、架构复杂、排错调试成本高

核心决策原则

  1. 先使用单 Agent 完整跑通业务流程；
  2. 只有出现三类瓶颈时，才拆分多 Agent：

  3. 拆分多 Agent 不是为了技术酷炫，是解决单 Agent 解决不了的实际瓶颈。

5.2 心跳：Agent Loop——模型天生只会一问一答，怎么让他持续多步自主执行？

一、核心概念：为什么需要 Agent Loop

原生大模型本身是单次一问一答，没有自主多步骤执行能力，只能输出一段文字，不会自动调用工具、循环推进任务。

Agent Loop（心跳循环） 是 Harness 运行时层的核心异步循环引擎（源码 query.ts 241 行 async function* queryLoop），通过死循环 + 异步生成器实现 ReAct 连续多轮自主执行，让模型自动完成「思考→调工具→看结果→再思考」的长链路任务。

流程：

  1. 程序调用 queryLoop 启动 Agent；
  2. 进入无限 while(true) 心跳循环；
  3. 每一轮内部：把历史对话、工具结果、用户问题打包给大模型，拿到模型输出；
  4. 代码检查模型有没有要求调用工具：
    • 有工具要执行 → needsFollowUp = true，不触发 break，继续下一轮循环；
    • 无工具、只有最终文字回答 → needsFollowUp = false，执行break，循环结束；
  5. 同时每轮计数turnCount，一旦跑满预设最大轮次，直接强制break，防止卡死；
  6. 循环结束后，把最终完整结果返回给用户。
1. 函数头部：async function* queryLoop(...): AsyncGenerator<QueryEvent>
  1. async：异步函数，用来对接大模型、API、文件读写这类网络 / IO 等待操作，不会卡死程序。
  2. function*：生成器函数，搭配 yield 可以分段、流式返回数据（聊天框打字实时输出、分步打印工具执行日志都靠它），不用等整段任务跑完才一次性返回结果。
  3. queryLoop：函数名，翻译为「查询心跳循环」，就是整个 Agent 持续多轮思考、调用工具的核心引擎。
  4. AsyncGenerator<QueryEvent>：返回异步生成器，每一轮循环向外抛出一个QueryEvent事件（比如：开始调用模型、执行工具、循环结束等事件），前端 / 日志系统可以实时接收。
作用：这个函数是 Agent 的心脏，负责驱动「思考→调工具→再思考」无限循环，同时支持流式实时输出。
2. 核心骨架：while (true) { }

while(true) 是无限死循环，也就是文档里说的心跳循环。

原生大模型只能一问一答，靠这个循环重复执行多轮任务，实现 ReAct 自主多步骤工作：

每一轮循环固定流程：

组装上下文 → 调用 LLM 大模型 → 接收模型回复 → 判断要不要继续干活

3. 两条循环终止 break 退出条件（满足任意一条，立刻跳出 while 循环，任务结束）
条件 1：if (!needsFollowUp) break;
  • needsFollowUp = 是否需要继续下一轮循环
  • 逻辑：如果不需要继续干活，直接跳出循环
  • 触发场景：大模型本轮输出纯文字答案，没有任何工具调用指令，代表信息齐全、任务做完了，正常结束对话。
  • 源码位置：第 1062 行
条件 2：if (turnCount >= maxTurns) break;
  • turnCount：当前已经跑了多少轮循环
  • maxTurns：预设最大允许循环轮次（比如限制最多 20 轮）
  • 逻辑：循环次数达到上限，强制终止
  • 作用：兜底防护，防止模型陷入无限死循环疯狂调用工具、无限消耗 Token、算力；属于熔断保护机制。
  • 源码位置：第 1704 行
关键补充

  1. 为什么要用async function*生成器？

    普通函数只能全部跑完一次性返回结果；生成器可以跑一轮就向外推送实时事件，实现聊天界面逐字流式输出、实时打印工具调用日志。

  2. 两条 break 分别管什么？

  • needsFollowUp：业务正常结束（事干完了主动退出）
  • turnCount >= maxTurns：安全兜底结束（防止死循环强制退出）

二、完整一轮循环执行流程

分步拆解

  1. 组装上下文

    把系统提示词、历史对话、用户最新输入、上一轮工具返回结果合并，喂给大模型。

  2. 流式调用 LLM

    采用异步生成器 async generator，支持流式输出实时返回内容（ yield 推送片段）。

  3. 解析模型返回

    不信任单纯的 stop_reason ，主动遍历返回内容，筛选类型为 tool_use 的工具调用块，收集本轮要执行的工具。

  4. 判定是否续跑（needsFollowUp）

    只要提取到有效工具调用块，就标记 needsFollowUp = true ，代表任务没做完，需要继续循环；无工具调用则标记为 false，准备退出。

  5. 执行工具动作

    批量运行所有提取出的工具，拿到外部数据（文件读取、API、知识库检索等结果）。

  6. 回填上下文

    将工具执行的输出追加到对话历史，回到循环开头，带着新信息重新提问大模型，开启下一轮思考。

三、底层源码关键逻辑说明

  1. 循环载体：while (true) 无限心跳

    while (true) 持续轮询，每一轮代表一次完整的「思考 + 行动」心跳，直到命中退出条件才终止。

  2. 异步生成器 async function + yield*

    不阻塞整体服务，支持流式分段输出内容，适配前端实时打字效果、长任务分段日志打印。

  3. 工具块强校验逻辑

    不依赖模型自带停止标识，强制解析消息内容里的 tool_use节点，避免模型漏标识工具调用导致循环提前中断。

5.3 记忆：上下文管理——跑着跑着就忘了，怎么办？

这套机制解决的核心痛点：多轮 Agent 循环后对话 Token 无限膨胀，触发模型上下文窗口溢出、丢失关键信息、算力成本暴涨。

整体分为两大模块：

  1. 四层逐级降级自动压缩（Snip → Microcompact → Context Collapse → Autocompact），从零成本轻量压缩到 LLM 摘要兜底；
  2. 双分区上下文隔离（可压缩区 + Protected Tail 保护尾），永远保留最新任务完整原文；
  3. 跨会话持久记忆（CLAUDE.md 项目规范记忆 + MEMORY.md 长期事实记忆），关闭会话不丢失历史经验。

一、四层自动压缩链路（逐级触发，优先零成本）

触发时机：上下文剩余 Token ≤ 13000 时，逐层执行压缩，每层压缩后校验 Token 占用，不够再进入下一层。

零 API = 完全不调用大模型推理接口，全部靠内存字符串遍历、结构化消息过滤、标记替换完成，只操作本地的对话消息数组，没有网络请求、不消耗llm计费token。

Agent 的对话上下文在内存里不是纯长文本，而是结构化消息数组：

每条消息固定带类型标记：user/assistant/tool_use/tool_result，工具返回有明确类型字段，代码可以直接筛选、裁剪、替换，不需要让模型理解内容。

1.原理：删除重复的FileRead文件读取返回内容

  1. 原理：把可重复执行的工具返回结果替换成极简占位符，需要时可重新调用工具还原完整内容

  2. 可清理工具列表

  1. 效果：几十行工具交互内容压缩成一句话，仅保留行为记录，释放大量窗口空间
第四层 Autocompact LLM 摘要压缩（兜底，消耗 1 次 LLM 调用）

前三层轻量化压缩后 Token 依然超标，启动最终兜底压缩

  1. 触发阈值：剩余 Token ≤ 13000，配置常量 AUTocompact_BUFFER_TOKENS = 13000，源码autoCompact.ts:62

  2. 核心分区机制：双区域隔离（Protected Tail 保护尾）

    • 可压缩区（早期历史）：多轮之前的工具调用、已解决问题、过往决策 → 全部交给 LLM 生成结构化精简摘要
    • Protected Tail 保护尾（永久原文保留，不参与压缩）：最近 N 轮完整对话、当前正在处理的任务、刚报错内容、当前操作文件路径

  3. 压缩后新上下文结构

  4. 优势：不会压缩当前正在处理的任务，避免模型遗忘当下步骤，同时清理老旧冗余历史

四层压缩优先级总结

优先执行零算力、零 API 损耗的三层轻量压缩，仅当轻量方案不足以释放窗口时，才调用一次 LLM 做全局摘要，最大化降低 Token 消耗成本。

二、Protected Tail 保护尾核心概念

1. 对话历史两大分区
分区 处理规则 存储内容
可压缩区 交给 LLM 压缩成摘要，丢弃原始完整内容 早期工具调用、已经解决完毕的问题、过去的历史决策
Protected Tail 保护尾 全程保留原始完整文本，绝不参与压缩 最近 N 轮完整对话、当前未完成任务、最新报错、正在操作的文件路径
2. 设计目的

如果直接把全部历史压缩，模型会丢失当前正在执行任务的细节，出现 “失忆、漏步骤、乱改代码”；

通过保护尾隔离新旧内容，老旧历史精简，当下任务完整留存，兼顾窗口大小与任务连续性。

  1. 执行 10 轮循环后上下文 Token 逼近窗口上限，剩余 13000Token，启动四层压缩；
  2. 第一层 Snip：删除多次重复读取的readFile重复文本；
  3. 第二层 Microcompact：把多次 web 搜索、shell 终端长输出替换为占位符；
  4. 第三层 Collapse：折叠前 5 轮工具调用配对为单行摘要；
  5. 三层轻量压缩后 Token 依旧超标，启动 Autocompact；
  6. 分区处理：前 7 轮老旧开发历史交给 LLM 压缩为摘要，最近 2 轮正在编写的接口代码、报错日志放入 Protected Tail 完整保留；
  7. 新上下文 = 历史摘要 + 最新两轮完整代码对话，继续循环开发；
  8. 开发中识别关键信息：项目统一用 pnpm、数据库 Bug 修复方案 → 自动写入当前项目根目录的MEMORY.md；
  9. 关闭当前对话框后，在同一个代码项目内重新打开新对话，会自动读取本项目的CLAUDE.md架构规范 + MEMORY.md历史踩坑经验，不用重复告知规则；
  10. 如果切换到另一个全新项目文件夹，会生成独立的记忆文件，旧项目的历史知识不会带入。

5.4 安全：刹车与护栏——能力越大，破坏力越大

模块归属 Harness 驾驭系统 Control 控制层（安全治理 Governance），核心思路：Agent 拥有文件读写、终端执行、网络请求等高权限操作，必须配套多层刹车 / 护栏，防止误删文件、篡改敏感配置、无限重试耗光 Token、高危命令越权执行。

整套体系分为三大块：

  1. 5 种全局权限运行模式（整机开关）
  2. 精细化工具权限规则 + 四层 Hook 硬拦截（实时行为管控）
  3. 连续失败熔断保护（故障止损，避免资源雪崩）

一、5 种全局权限运行模式（整机开关，一键切换 Agent 行为约束）

模式名 核心含义 典型使用场景
default 默认模式：每一次工具调用都会弹窗，等待用户手动确认后执行 日常本地开发，兼顾安全与可控，防止静默删文件
acceptEdits 自动放行全部文件编辑类操作（FILE_EDIT/FILE_WRITE），其余高危操作仍弹窗确认 完全信任 Agent 改代码，批量重构、自动写业务代码
plan 只读锁死模式：仅允许读文件 / 搜索，拒绝所有写入、终端修改类操作 初次探索代码库、做项目规划，防止误改动源码
dontAsk 全自动无弹窗，所有合规工具直接静默执行，无需人工确认 自动化脚本、定时批量任务、无人值守 Agent 流程
bypassPermissions 完全跳过全部权限校验逻辑，无任何拦截 内部受控沙箱环境、测试调试场景，生产环境禁止使用
精细化权限规则底层逻辑

权限规则标准公式：工具名 + 行为策略(allow/ask/deny) + 调用来源

三种行为策略：

  1. allow：永久自动放行，不弹窗、不拦截
  2. ask：每次调用弹出确认窗口，人工审核后执行
  3. deny：永久直接拦截，拒绝执行，返回权限错误
规则示例
  1. Bash(npm run test) → allow：执行单元测试命令永久放行
  2. Bash(rm) → ask：删除文件类 shell 命令每次弹窗确认
  3. Write(.env) → deny：永远禁止修改环境变量敏感配置文件

二、四层 Hook 拦截钩子（全生命周期硬拦截，底层强制管控）

Hook 是嵌入 Agent 全流程的拦截入口，无视模型输出，在动作发生前后强制校验、拦截、记录，属于底层硬护栏，Prompt 文字无法绕过。

Hook 钩子名称 触发时机 典型业务用途
UserPromptSubmit 用户输入发送给 LLM 之前 提前注入项目规范 CLAUDE.md、过滤用户危险输入、校验指令合规性
PreToolUse 工具发起执行之前 核心安全拦截层：校验 bash 命令是否高危、文件路径是否敏感、匹配 deny 权限规则直接阻断越权操作
PostToolUse 工具执行完成、结果返回 LLM之后 校验工具输出内容、自动记录操作日志、代码修改后自动 git commit 保存变更
Stop Agent 任务循环终止、会话关闭时 自动持久化 MEMORY.md 记忆、清理临时缓存文件、释放运行资源
核心价值

哪怕 LLM 输出删除数据库、修改.env 的指令，PreToolUse钩子会在工具运行前直接拦截，不会执行高危操作，仅靠提示词约束无法实现这种底层强制阻断。

三、失败熔断与重试止损机制（防止无限循环消耗 API/Token）

1. 核心常量阈值

连续 3 次压缩失败，直接触发熔断终止循环。

三类失败分级处理逻辑
① 单次工具调用执行失败（如 shell 命令报错、文件不存在）

流程：

工具执行报错 → 错误信息注入上下文 → LLM 读取错误日志 → 自主调整方案重试工具

特点：允许自主重试，不会直接熔断，属于业务正常纠错。

② LLM 模型接口调用失败（网络超时、限流、500）

流程：

采用指数退避策略，最多重试 3 次；3 次全部失败后，直接抛出错误终止任务，返回失败给用户。

③ 上下文 AutoCompact 压缩连续失败（核心熔断场景）

完整链路：

prompt_too_long（上下文溢出） → 触发 reactive_compact 自动压缩

→ 压缩执行失败 → 重复重试压缩

→ 连续失败达到阈值 3 次 → 熔断保护，强制停止 Agent 循环，不再发起 LLM 压缩 API 调用，避免无限消耗计费 Token。

熔断设计目的

防止极端死循环：上下文持续溢出 + 压缩永久失败，反复调用 LLM 做摘要，持续产生高额 Token 消耗，熔断直接切断循环止损。

四、整套安全体系串联实战举例（编码场景）

  1. 运行模式切换为acceptEdits：自动放行代码文件编辑；
  2. Agent 输出指令Write(.env)修改环境变量文件；
  3. 进入PreToolUse钩子，匹配权限规则Write(.env) → deny，底层直接拦截，工具不会执行；
  4. 若 Agent 执行rm -rf src/删除源码，匹配Bash(rm) → ask，弹出确认窗口等待人工审核；
  5. 工具执行完成触发PostToolUse钩子，自动把代码变更提交 git；
  6. 上下文持续膨胀，启动四层 Autocompact 压缩，连续 3 次压缩接口报错；
  7. 触发熔断保护，终止心跳循环，返回任务失败，不再重复调用 LLM 消耗资源；
  8. 用户关闭对话触发Stop钩子，自动把项目关键规则写入 MEMORY.md 持久保存。

5.5 能力：工具与技能——Agent 的手和脚

一、单工具完整生命周期（5 步流水线，工具调用全校验流程）

整体执行顺序

任意一步校验失败，直接终止，不会走到真实执行逻辑。

① ToolDef 工具静态定义（每个工具标准化元数据）

每个工具提前写死配置，同时供给系统校验和LLM 识别：

  1. name：工具唯一标识（如FILE_READ、BASH、WEB_SEARCH）
  2. inputSchema：Zod 强类型约束，规定入参字段、类型、必填项、格式、长度限制
  3. description 给 LLM 阅读：说明工具用途、适用场景，让模型自主判断何时调用该工具
  4. prompt：该工具专属系统提示词，触发工具时临时注入上下文
② validateInput 输入强校验（前置防幻觉报错）

LLM 输出工具调用参数后，不直接执行，先用 Zod Schema 校验：

  • 缺失必填参数、字段类型错误、非法路径、超长字符串 → 直接拒绝执行

  • 把参数错误信息注入上下文，让 LLM 修正参数后重新调用

    作用：提前拦截模型幻觉生成的非法参数，避免执行时报错浪费 Token 与接口调用。

③ isConcurrencySafe 并发安全校验

判定工具是否支持多实例并行执行：

  • 默认值false：绝大多数文件读写、终端、写文件工具不支持并发，同一时间仅能跑 1 个实例，防止文件锁、内容覆盖冲突
  • 仅纯读无状态工具（网页检索、只读知识库查询）标记为true，允许多个并行调用
④ checkPermissions 权限安全校验（PreToolUse 钩子核心）

结合当前会话全局权限模式（default/acceptEdits/plan/dontAsk/bypassPermissions）匹配规则，返回三种结果：

  • allow：自动放行，直接进入执行

  • ask：弹出人工确认弹窗，用户同意后放行

  • deny：永久直接拦截，拒绝执行

    高危操作（删除文件、修改.env、高危 rm 命令）在此层底层拦截，不受 Prompt 文字约束。

⑤ call 真实执行逻辑

前 4 层校验全部通过后，运行工具底层业务逻辑；

执行完成后，工具输出结果由 Harness 自动注入对话上下文，回到 Agent 心跳 Loop 开启下一轮思考。

配套常量

含义：常驻 Skill 极简列表，仅占用总上下文 1% Token 配额，对应下方「两级 Skill 按需加载」机制，控制常驻工具描述不挤占窗口空间。

二、Skill 两级渐进式披露（解决工具过多导致 System Prompt 爆窗口）

核心痛点

如果把项目几十种工具完整描述一次性塞进系统提示词，会瞬间占满上下文窗口，触发prompt_too_long溢出；

解决方案：分两阶段按需加载，仅保留极简常驻列表，需要时再注入完整配置，任务结束立刻回收。

阶段一：常驻 Skill 列表（全局永久存在，仅占 1% 上下文）
  • 内容：只展示工具名称 + 一句话极简功能描述
  • 作用：让 LLM 知道「当前系统具备哪些能力」，但不加载冗长参数、完整提示词、领域文档
  • 开销极低，严格限制总 Token 仅占上下文 1%，不会溢出
阶段二：按需加载完整 Skill（临时注入，用完销毁）

  1. LLM 判断当前任务需要某一项专业能力 → 主动调用SkillTool

  2. 系统一次性注入该 Skill 全套内容：完整 System Prompt、Zod 参数 Schema、领域专业知识

  3. 该任务全部完成后，完整 Skill 内容从上下文清除，退回阶段一极简常驻列表

    优势：大量工具不会常驻占用窗口，实现按需扩容、自动回收，大幅缓解上下文膨胀。

三、Plan Mode 规划模式 + TodoWrite 断点任务编排（长复杂任务流水线）

1. Plan Mode 规划模式切换机制（EnterPlanModeTool）
底层原理

不是单纯给 LLM 一段提示词，而是修改全局会话运行状态，变更权限模式：

Plan Mode 固定流程（以「重构认证系统」为例）
  1. 自动切换为plan只读权限模式：仅允许文件读取、搜索，禁止一切写文件 / 终端修改操作，避免规划阶段误改动代码
  2. Agent 遍历代码库、梳理依赖、拆解全局任务，拆分为多条子任务清单
  3. 输出全局路线图给用户确认
  4. 用户确认完成，自动退出 Plan 模式，切换回可编辑权限
2. TodoWrite 任务状态管理 + 断点续跑
三种任务状态
  • pending：待开始
  • in_progress：正在执行（同一时间只能有一个进行中任务，串行执行）
  • completed：已完成
核心价值
  1. 长任务拆分为有序子任务，逐条流转状态；
  2. 中途任意步骤报错、上下文压缩、会话重启，读取 Todo 清单就能定位到执行断点；
  3. 从失败的子任务继续执行，不用从头重做全部流程。
举例

任务清单：

  1. 重构 token 生成逻辑 → pending → in_progress → completed

  2. 更新中间件 → pending → in_progress → 执行报错

    Agent 重启 / 压缩后读取 Todo，直接从「更新中间件」这条断点继续执行，无需重复完成第一条已做完工作。

四、整体串联实战举例（Vibe Coding 大型重构场景）

  1. 会话启动，上下文仅加载阶段一极简 Skill 列表（占用 1% 窗口）；
  2. 用户需求「重构认证系统」，Agent 调用EnterPlanModeTool切换只读 plan 模式；
  3. 规划阶段仅启用FileRead工具，走完整工具 5 步校验流水线读取项目代码；
  4. 拆解 7 条子任务生成 Todo 清单，用户确认后退出 Plan 模式；
  5. 进入 TodoWrite 串行执行每条子任务，执行前按需加载对应完整 Skill；
  6. 每条子任务调用工具时，依次经过参数校验、并发检查、权限校验后执行；
  7. 中途某条代码修改报错，记录任务状态；上下文 Token 超标自动四层压缩；
  8. 压缩完成后读取 Todo 清单，从失败的子任务断点继续执行，无需从头重构。

5.6 协作：多 Agent 编排——一个脑子同时干所有活，会混

核心核心痛点

单个 Agent 同时兼顾「需求分析、架构规划、写代码、自测、代码审查」，大量无关信息混在同一份上下文里，思路混乱、工具权限混杂、容易幻觉出错。

解决方案：拆分成多子 Agent 分工隔离，每个子智能体独立上下文、独立工具集、单一岗位职责，互不干扰。

一、标准样例：Orchestrator-Workers 调度 - 工人架构

整体架构分层

  1. 主 Agent Orchestrator（总调度）

    唯一总控大脑：接收用户原始需求、拆分任务、下发给各个子 Agent、收集所有子 Agent 产出、整合最终结果交付用户。

  2. 三类隔离子 Worker（互相完全隔离，不共享上下文、工具互不通用）

SubAgent A：Planner 规划智能体
  • 独立上下文：只加载产品需求文档，看不到项目源码
  • 开放工具：仅FileRead只读文件，无写文件、终端高危权限
  • 输出产物：项目整体拆解规划文档、分阶段任务清单
  • 职责：只做方案设计、梳理依赖，不写任何业务代码
SubAgent B：Coder 编码开发智能体
  • 独立上下文：仅加载 Planner 输出的规划文档 + 项目源码
  • 开放工具：FileRead/FileWrite/Bash，完整读写、执行终端权限
  • 输出产物：完整代码文件变更、接口逻辑、业务实现
  • 职责：只落地编码实现，不做全局架构评审
SubAgent C：Reviewer 代码审查智能体
  • 独立上下文：仅加载 Coder 产出的代码 diff 变更记录
  • 开放工具：FileRead/Playwright，读代码、浏览器页面预览
  • 输出产物：审核结论（通过 / 驳回）+ 精准缺陷修改建议
  • 职责：只校验漏洞、边界问题，禁止直接修改代码
Orchestrator-Workers 架构核心优势
  1. 上下文彻底隔离：规划、编码、评审数据互不混杂，不会互相干扰模型思路；
  2. 工具权限精细化切割：规划阶段只有只读权限，杜绝误删源码；编码放开全操作权限；评审仅校验权限；
  3. 可并行执行：多个 Coder 子 Agent 可同步开发不同业务模块，加速大型项目；
  4. 模块解耦：可单独迭代优化规划、编码、审查能力，互不影响整套流程。

二、三大主流多 Agent 协作模式对比

协作模式 内部结构 运行逻辑 底层依赖 典型适用场景
Orchestrator-Workers调度者 - 工人 1 个总调度 Agent + 多个独立 Worker 子 Agent 调度者统一拆分、分发、汇总任务；Worker 独立干活，Worker 之间不直接通信 Claude Code SubAgent 原生方案，依靠文件中转传递产出 单一代码项目内大型工程重构、完整产品开发（图中示例）
Peer-to-Peer对等互通 无上下级，全部 Agent 地位平等 Agent 之间可自主互相委托任务，按需跨领域协作，无需统一调度中转 A2A（Agent-to-Agent）通用通信协议 跨厂商、跨系统、跨企业多智能体联动（客服 Agent + 数据分析 Agent）
Pipeline线性流水线 Planner → Generator → Evaluator 串行流转 上一个 Agent 的输出，强制作为下一个 Agent 唯一输入；层层校验，无法跳过评审环节 上下文串行单向传递，每一步输出必须流入下一关卡 高严谨性场景：金融代码、合同审查、学术论文、合规开发

三、三种模式通俗类比区分

  1. Orchestrator-Workers（项目开发团队）

    项目经理（Orchestrator）接收需求，拆分三份工作，分别交给架构师、开发、测试；三人独立工作，全部成果汇总给项目经理统一交付。

  2. Peer-to-Peer（跨公司业务对接）

    电商客服 Agent 遇到退款财务问题，直接自主呼叫财务数据分析 Agent，双方平等互通，不需要统一总调度中转。

  3. Pipeline（金融合规流水线）

    架构方案必须交给开发实现，开发完成的代码强制流入评审，评审不通过直接打回重写，不能跳过任何一道校验环节。

四、存储与运行补充

  1. 每个 SubAgent 拥有完全独立的会话内存上下文，互不共享消息数组；
  2. 子 Agent 产出的规划文档、代码 diff 会落地项目磁盘临时文件，供调度者分发传递；
  3. 多 Agent 调度规则、子 Agent 隔离配置固化在框架底层subagent/源码目录，全局静态配置；
  4. 所有子 Agent 执行过程会生成独立 OTEL 追踪 Span，统一进入观测日志复盘。

本模块解决两大核心生产问题：

  1. 可观测（Otel 埋点 + 配套工具）：全链路采集 Agent 运行数据，看清「Token 消耗、报错、耗时、成本流向」；
  2. 验证评估（六层测试 + 量化指标）：分层自动化校验 Agent 能力，用标准化数值衡量稳定性、故障定位能力，判定是否具备上线投产条件。

评估方案 失败检测召回率 失败根因准确率
仅端到端整体评估 0.41 无（无法定位出错环节）

解读：DAG 分层评估会按照 Agent 执行链路拆解节点，既能大幅提升故障检出率，又能精准定位出错环节。

2. 两大投产可靠性判定指标
  1. pass@k：Agent 重复运行 k 次，至少成功 1 次的概率，代表任务执行天花板上限；
  2. pass^k：Agent 连续跑 k 次全部成功的概率，代表稳定性底线。
投产判定标准举例
  • 不可投产：pass@5=0.9，pass^5=0.4 → 连续 5 次全部成功仅 40%，波动极大
  • 谨慎投产：pass@5=0.85，pass^5=0.75 → 连续五次全成功概率 75%，稳定性达标

一、核心总公式（整套 Agent 系统的评判标准）

公式原文

只优化提示词、只换更强的大模型，做不出稳定可投产的商用 Agent；必须补齐整套 Harness 驾驭系统全部配套工程模块。

二、5 条底层工程铁律（所有模块统一遵守的硬性设计准则）

铁律 1：不信任模型，信任系统
含义

大模型天生不靠谱，存在很多固有缺陷：

  1. 模型自带随机性，stop_reason标识经常出错，会隐瞒工具调用、截断输出；
  2. 很容易无视 System Prompt 里的文字约束，私自执行高危删除、修改密钥等操作；
  3. 经常选错工具、填错非法参数、产出幻觉指令。

Harness 系统的定位：不奢求模型永远不出错，而是就算模型犯错，底层系统也能拦住、兜底、止损。

实战例子

哪怕模型输出rm -rf /删除根目录的高危指令，前置 PreToolUse 钩子、权限规则会在执行前直接拦截，不会真实执行；不靠 Prompt 文字劝阻模型，靠底层代码护栏兜底。

铁律 2：失败关闭 Fail Closed（安全兜底核心策略）
含义

系统无法判断当前操作是否安全时，宁可直接拒绝执行，绝不冒险放行；

权限优先级固定：deny（拒绝） > ask（弹窗确认） > allow（自动放行）；系统默认判定所有操作不安全。

落地规则
  1. 未知文件、陌生 Shell 命令、不认识的工具操作，默认直接 deny 拦截；
  2. 删除文件、修改.env密钥文件、高危删除 rm 命令，默认走 ask 弹窗人工确认；
  3. 仅白名单内安全测试命令（如npm run test）才会 allow 自动放行。
反向对比（生产严禁使用）

Fail Open（失败开放）：拿不准就直接放行，一旦模型产生幻觉，会直接破坏代码、数据库、配置文件，仅隔离沙箱测试环境可用。

铁律 3：机械强制优于文本规劝
含义

底层代码 Hook 拦截、参数强校验、权限系统这类代码层面硬性约束，优先级远远高于 Prompt 里的文字提醒。

正反对比
  • 低效方案（文本规劝）：System Prompt 写十句 “禁止修改.env 环境文件”，模型依然大概率忽略文字约束；
  • 可靠方案（机械强制）：PreToolUse 钩子硬编码拦截Write(.env)操作，无论模型输出任何指令都直接阻断，Prompt 文字完全无法绕过底层拦截。
延伸准则

所有安全、行为约束依靠代码实现，不能寄希望于模型看懂文字、自觉遵守。

铁律 4：每遇到一个错误，就工程化一个解决方案
理念来源

Mitchell Hashimoto（HashiCorp 创始人，云原生基础设施工程理念）

含义

不要只临时修复单次偶然 Bug，要搭建一套通用工程机制，让同类错误永久不再出现。

实战举例

  1. 问题：频繁出现上下文过长溢出prompt_too_long报错；

    短期临时修复：单次手动精简对话；

    工程化根治方案：落地四层自动压缩整套机制，所有长对话自动精简，同类溢出问题永久根治。

  2. 问题：模型频繁幻觉误删源码；

    工程化方案：搭建文件操作权限白名单 + rm 类命令弹窗确认机制，彻底杜绝批量误删。

铁律 5：成功应该沉默，失败才出声
含义

反馈机制要节省上下文 Token，不占用窗口空间：

  1. 合规、正常、成功执行的工具、流程，静默运行，不弹窗、不插入冗余确认文本；
  2. 只有异常、高危、失败场景才打断流程、弹窗确认、写入报错日志。
好处

避免大量成功确认文本塞满上下文，大幅降低prompt_too_long溢出概率，减少无效 Token 消耗、节省算力成本。

实战例子

acceptEdits自动编辑模式下，正常业务代码修改静默完成；只有执行删除文件、修改密钥配置时，才弹窗提醒人工确认。

三、整套体系串联落地总结

  1. 判断 Agent 真实交付能力不能只看模型本身，要用乘法公式完整评估七大配套模块；
  2. 上下文压缩、工具、权限、记忆、钩子、测试可观测全部功能，统一遵循 5 条底层铁律设计；
  3. 整套架构核心思想：不依赖模型自觉自律，靠一套完整、强约束、可自愈的 Harness 系统兜底，实现安全、稳定、可投产的长流程自主 Agent。

6.1 AI + 全栈：Vibe Coding 核心优势

核心结论：懂全栈的人用 AI，需求清晰、能看懂 AI 输出、能校验最终成品；不懂全栈只会模糊提问，AI 产出极易报废

6.2 互联网基础：从输入 URL 到看到网页

底层原理，所有 Web 项目的通用底层逻辑

  1. 互联网工作整体流程：输入域名 → DNS 解析 IP → HTTP/HTTPS 请求传输 → 服务器返回代码 → 浏览器渲染页面
  2. HTTP / HTTPS
    • HTTP：明文传输，数据裸奔，容易被窃听篡改
    • HTTPS：带 SSL/TLS 证书加密传输，浏览器标安全锁，国内上线强制要求
  3. DNS 与域名：域名（shturl.）和服务器 IP 地址的翻译系统，人记域名、网络识别 IP
  4. 浏览器渲染：拿到 HTML/CSS/JS 后，解析、排版、绘制出页面给用户
  5. 托管 Hosting：存放网站代码 / 服务的线上平台（Vercel、阿里云、AWS 等）

6.3 前端：用户看到什么

前端 = 浏览器里展示、交互的页面代码，分层基础技术栈

  1. 三大基础原生语言
    • HTML：网页骨架，定义页面按钮、输入框、文字结构
    • CSS：网页皮肤，控制颜色、布局、尺寸、样式
    • JavaScript：网页行为，点击弹窗、表单提交、页面切换交互逻辑
  2. TypeScript：JS 超集，增加类型约束，避免参数、变量幻觉报错，大型项目必备
  3. 前端三选一主流框架：React / Vue / Angular，封装复用组件，不用重复写原生 HTML
  4. Tailwind CSS：原子化 CSS 框架，不用手写独立样式文件，快速写响应式页面
  5. npm 包管理器：下载、管理第三方代码工具（组件、图表、请求库）

6.6 版本管理与 CI/CD：代码怎么管、怎么自动上线

一、先搞懂两个核心概念

1. CI/CD 流水线（Pipeline）

定义：一套自动化流程，把「代码提交→编译→测试→打包→发布」全链路串起来，不用人工一步步点按钮。

完整阶段：

  1. 拉取代码（Git/Gitlab/Gitee）
  2. 代码检查、单元测试、静态扫描
  3. 编译打包（jar、docker 镜像、rpm、前端 dist、AI Agent 脚本包）
  4. 制品上传存储（存入制品库）
  5. 环境部署（测试 / 预发 / 生产）
  6. 自动化回归测试、监控告警

核心价值：标准化、可重复、自动卡点，上线不依赖人工操作。

2. 制品库（Artifact Repository）

制品：代码编译 / 打包后产出的交付物，不是源码，是可直接运行的包：

Java jar、Python whl、Docker 镜像、Node npm 包、二进制程序、AI 工具 Skill 压缩包、配置文件。

制品库：专门统一存放、版本管理、权限管控所有交付包的仓库，替代本地磁盘、随便传文件、共享文件夹。

能力：版本追溯、权限隔离、加速下载、漏洞扫描、清理过期包、跨环境分发。

二、Jenkins：主流流水线调度工具（流水线载体）

核心定位

专门用来跑 CI/CD 流水线的调度引擎，负责编排整个自动化流程。

核心能力

  1. 流水线编排

    支持 Jenkinsfile（代码化流水线，存 Git 里，版本跟着项目走），用声明式脚本定义每一步动作：拉代码、测试、打包、上传制品库、部署。

  2. 插件生态极强

    对接 Git、JUnit 测试、Sonar 代码扫描、JFrog 制品库、K8s、Docker、OTEL 监控等几乎所有工具。

  3. 分布式构建

    多台代理节点分担打包、测试任务，不会单台机器卡死。

  4. 质量门禁

    单元测试通过率、代码覆盖率、漏洞数量不达标，直接终止流水线，禁止打包上传制品。

典型流水线执行流程（Jenkins）
  1. 开发提交代码到 Git → Webhook 自动触发 Jenkins 流水线
  2. Jenkins 拉取源码，执行单元测试、代码安全扫描
  3. 编译打包生成制品（jar / 镜像 / Agent 工具包）
  4. 调用 JFrog 插件，把包上传到制品库，打上版本号、分支标签
  5. 从制品库拉取对应版本包，部署到测试环境
  6. 自动跑自动化测试，失败则触发告警，终止发布
局限

Jenkins 只负责流程调度，不负责长期存储制品，打包产物不能长期存在 Jenkins 服务器（磁盘易满、无版本管理、无权限隔离），所以必须搭配制品库 JFrog。

三、JFrog（Artifactory）：企业级统一制品库（存储载体）

核心定位

统一存放所有类型软件交付包的制品仓库平台，行业标准企业级制品库，替代简陋的 Nexus。

核心能力

  1. 全类型制品统一管理

    支持 Docker 镜像、Maven/Jar、NPM、Python、Go、rpm、deb、二进制、压缩包（你的 Agent Skill 工具包也能存）。

  2. 版本全生命周期管控

    每个包记录：构建人、构建流水线编号、Git 提交记录、构建时间，可一键回滚旧版本。

  3. 权限分级隔离

    测试人员只能下载测试版，生产账号仅允许拉取稳定发布包，禁止开发直接覆盖线上版本。

  4. 漏洞安全扫描

    上传制品自动扫描依赖漏洞、恶意代码，高危包直接拦截，禁止部署。

  5. 缓存加速、异地分发

    内网缓存公共依赖，外网拉取一次后本地复用，大幅提升 Jenkins 打包速度；多机房远程同步制品。

  6. 清理策略

    自动清理几个月未使用的测试临时包，释放存储。

和 Jenkins 的配合关系

Jenkins 是「包工头」，负责指挥干活（测试、打包）；

JFrog 是「仓库库房」，专门永久存放打包好的成品，统一保管、管控安全与版本。

四、Jenkins + JFrog 完整协同链路

以你开发 AI Agent、自定义 Skill 工具举例：

  1. 开发者提交 ToolDef、Skill 源码到 Git 仓库
  2. Git 触发 Jenkins 流水线启动
  3. Jenkins 阶段 1：单元测试（对应六层测试 Layer1）、代码静态扫描
  4. Jenkins 阶段 2：打包所有 Skill、Agent 框架，生成 zip 制品
  5. Jenkins 阶段 3：调用 JFrog 插件，上传制品到 JFrog 制品库，标记版本号、分支、构建 ID
  6. JFrog 自动扫描包内依赖漏洞，存在高危漏洞直接拒绝入库，流水线失败
  7. 测试环境部署：Jenkins 从 JFrog 拉取对应版本 Agent 包，部署测试沙箱
  8. 自动执行 AgentEval、pass@k 评测（对应验证质量模块），评测通过后，允许将制品提升为生产可用版本
  9. 生产发布：Jenkins 从 JFrog 拉取稳定版制品，上线生产环境，所有版本记录永久存在 JFrog 可追溯

五、表格清晰区分两者

工具 定位 核心职责 类比 能否单独使用
Jenkins CI/CD 流水线调度引擎 编排自动化流程：拉代码、测试、编译、触发上传 / 部署 工地包工头，安排施工步骤 可以单独跑测试打包，但无长期制品存储能力，不适合企业生产
JFrog Artifactory 企业级统一制品库 存储、版本管理、安全扫描、权限管控所有打包交付物 成品仓库，统一存放完工产品 可以单独存包，但没有自动构建、测试能力，需要流水线触发上传

六、关键总结

  1. 流水线 Pipeline：自动化交付全流程；制品库：统一存放打包后的交付产物；
  2. Jenkins = 流水线执行工具，负责「怎么做」；
  3. JFrog = 制品存储平台，负责「存哪里、管版本、控安全」；
  4. 生产环境必须二者搭配：Jenkins 自动构建产出包，JFrog 统一保管所有版本交付物，实现可追溯、安全、标准化发布。

6.8 域名与备案：在中国上线的合规链路

国内网站公网访问必须走完整套备案流程，否则服务器会被关停

完整合规步骤

  1. 域名注册 + 域名实名（必须和备案主体一致）
  2. 提交备案材料：身份证 + 服务器证书
  3. 服务商初审（12 工作日）→ 工信部短信核验（24h 内）→ 管局终审（120 工作日）
  4. 下发 ICP 备案号，网站底部必须悬挂
  5. ICP 通过后 30 天内完成公安备案

避坑指南

踩坑场景 解决方案
域名未实名 备案前完成域名持有者实名认证
备案信息不一致 域名持有者 = 备案主体，名称一字不能差
备案审核中 管局审核期间网站必须关闭，不能对外访问
忘记公安备案 ICP 下发 30 天内完成公安备案，逾期关停站点

6.9 安全与测试：让产品可信、可靠

一、基础安全体系

  1. HTTPS / SSL 证书：全站加密传输，防止请求数据被窃取篡改

  2. OWASP Top10

    ：Web 十大高危漏洞行业标准，下面 3 个是最常见攻击：

    • XSS 跨站脚本：恶意脚本注入页面窃取用户 Cookie → 所有前端用户输入做转义过滤
    • SQL 注入：输入框拼接恶意 SQL 偷取、删除数据库数据 → 使用 ORM / 参数化查询，禁止拼接原生 SQL
    • CSRF 跨站请求伪造：诱导用户非自愿执行操作（转账、改密码）→ 接口增加 CSRF Token 校验

  3. 密钥管理：数据库密码、第三方 API 密钥、JWT 密钥统一安全存储，禁止硬编码写代码、提交 Git

七、具身智能：AI从2数字世界走向物理世界

具身智能 = 拥有实体硬件（机器人、机械臂）的 AI，不再只在代码里处理文字，能看懂真实环境、规划动作、操控物理设备完成现实任务；整套图谱分为 6 大模块：核心三要素、六层技术栈、仿真训练、演进时间线、七大前沿研究方向、产业落地现状。

7.1 具身智能三大核心要素

机器人能干活缺一不可，类比人类：

  1. 大脑：各类大模型（LLM/VLM/VLA/ 世界模型），负责理解指令、规划任务、预判物理结果、反思纠错
  2. 身体：实体硬件（相机、雷达、机械臂、电机、NPU 计算芯片），负责感知环境、执行物理动作
  3. 环境：机器人所处真实物理空间 / 数字仿真场景（仓库、家庭、工厂、虚拟模拟器），所有交互的载体

7.2 六层分层核心技术栈（从底层硬件到上层 AI 大脑）

自下而上逐层依赖，下层支撑上层决策

分层 核心功能 通俗解释 + 关键技术
硬件层（最底层） 感知硬件 + 执行硬件 + 本地计算 深度相机、激光雷达、电子皮肤感知外界；电机、灵巧手做抓取 / 移动；板载 NPU 在机器人本地完成 AI 推理，不用依赖云端
控制层 运动精准执行、实时微调 规划移动路线、计算机械关节角度，用 MPC、强化学习修正动作，防止撞物体、抓东西滑落
智能体层（LLM 任务规划） 长任务拆解、记忆、自我反思 把 “拿苹果” 拆解成：走到冰箱→打开门→抓取苹果→放回桌面；记住历史操作，做错后复盘优化流程
模型层（VLA + 世界模型） 端到端视觉语言动作、物理预判 VLA 模型：看图片 + 文字指令直接输出机械动作；世界模型：提前预判物体掉落、碰撞等物理后果；代表：RT-2、OpenVLA、Octo
感知层 看懂环境、定位自身、多感官融合 视觉拍照、触觉感应、SLAM 地图定位；融合多传感器信息，让机器人知道「自己在哪、面前是什么、摸到了什么」

7.3 仿真与训练体系

1、为什么必须用仿真模拟器？

真实物理世界训练成本极高、速度慢、危险：

  • 真机反复抓取会磨损硬件，摔损维修成本高；
  • 机器人试错一次耗时几秒；仿真一天可完成百万次试错；
  • 高危动作（搬运重物、高速移动）不会损坏实体设备。

2、五大主流工业仿真平台

  1. NVIDIA Isaac Sim：工业机器人、自动驾驶标杆，支持高精度物理引擎
  2. MuJoCo：强化学习标配，轻量、运动动力学计算精准
  3. Gazebo：和 ROS 机器人系统深度集成，开源通用
  4. Habitat（Meta）：专注室内家庭导航、家居交互仿真
  5. ManiSkill：灵巧手抓取、精细操作专项仿真

3、Sim2Real 仿真迁移核心难题 & 解法

问题：仿真里能完美完成任务，放到真实机器人直接失效（光影、摩擦力、物体尺寸存在数字和现实差异）

解决方案：域随机化，训练仿真时主动随机修改光照、物体纹理、摩擦力、相机噪声，强制模型适应现实环境的不确定性，大幅提升真机成功率。

7.4 具身智能架构演进时间线（2023–2026）

  1. 2023：单点割裂阶段

    LLM 语言大模型、视觉感知、运动决策互相独立，需要人工写大量胶水代码串联，无法端到端联动。

  2. 2024：VLA 模型兴起

    视觉 + 语言 + 动作三合一模型诞生，感知、决策、行动打通，输入图片 + 文字直接输出机械动作，省去多层人工拆解。

  3. 2025：世界模型元年

    机器人拥有「物理直觉」，能提前预判物体运动、碰撞、掉落等因果结果，不会盲目执行动作。

  4. 2026（当前）：融合架构成熟

    大语言模型 + 世界模型联合架构，语义逻辑推理和物理仿真深度绑定，既能听懂复杂人类指令，又懂现实物理规则。

7.5 七大前沿重点研究方向

  1. VLA 端到端视觉语言动作模型

    行业主流路线，一张图像 + 自然语言指令直接输出机器人动作，实现零样本泛化，陌生物体、新任务不用单独训练。

  2. 世界模型构建

    给机器人搭建虚拟物理大脑，具备因果预测、反事实推理能力，预判操作会带来什么后果，规避危险动作。

  3. Sim2Real 无损域迁移

    极致域随机化技术，仿真训练成果几乎无损迁移到真机，行业最优方案任务成功率突破 98%。

  4. 真实 + 仿真混合数据集

    开源数据集 Open X-Embodiment，融合全球各类机器人真机 + 仿真操作数据，提升跨机器人、跨场景泛化能力。

  5. 安全可信规划框架

    Intel PMDF 三层可信体系：规划层 - 执行层 - 系统层全链路校验，防止机器人越权、做出危险操作（对应之前 Harness「不信任模型，信任系统」铁律）。

  6. 神经形态低功耗计算

    脉冲神经网络、类脑芯片，机器人本地端侧低功耗 AI 推理，适合电池供电的家用小型机器人。

  7. 群体分布式具身智能

    多机器人去中心化协同作业，自动拆分任务、互相配合，不用中央统一调度，适合工厂、仓储集群机器人。

7.6 国内产业落地现状

  1. 产业规模：国内具身智能核心企业超 350 家，建成专业机器人训练场地 30 + 个，总场地面积超 10 万㎡

  2. 落地场景成熟顺序（从易到难逐步商业化）

    智能制造工业机械臂 → 仓储物流搬运机器人 → 特种巡检机器人（电力、矿山） → 医疗康复机器人 → 家用服务人形机器人

    工业、物流场景技术门槛最低，当前落地最多；家庭人形机器人还处在试验阶段。
